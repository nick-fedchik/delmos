# DELMOS — Discovery, Engineering & Lifecycle Management Operating System

[![License](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](LICENSE)

**Репозиторій:** <https://github.com/nick-fedchik/delmos>

**DELMOS** — це відкрита автономна операційна система інженерного життєвого циклу (**ELM**) та проєктної економіки (**Project ERP / PPM**). Платформа призначена для наскрізного супроводу високотехнологічних продуктів у критичних галузях (Automotive, Aerospace, Medical Devices, Robotics, Industrial IoT): від попереднього аналізу запитів і науково-дослідних робіт до системного проєктування, розробки апаратного та програмного забезпечення, контролю бюджетів та проходження сертифікаційних аудитів.

**Стан проєкту:** документаційний/передкодинговий етап. Описані функції, адаптери та галузеві модулі є цільовою архітектурою, а не реалізованим продуктом. У цій директорії ще немає сервера, вебзастосунку, Makefile чи пройдених тестів PostgreSQL; машинні контракти першого зрізу валідовані лише структурно.

## 1. Ключові концептуальні стовпи

1. **Повний інженерно-бізнесовий контур (Full-Cycle Engineering & Economics):**
   * **Pre-sales & Bidding:** аналіз RFQ/RFP, оцінка технічної здійсненності (Feasibility), калькуляція собівартості та формування комерційних пропозицій.
   * **Research & R&D Spikes:** фіксація дослідницьких звітів, прототипів (PoC), порівняння мікроконтролерів і технологій за статтею витрат OpEx.
   * **Мультидисциплінарна інженерія (HW + SW + Mechanics):** системні вимоги, схемотехніка, BOM, специфікації випробувань поруч із кодом і прошивками.
   * **Project Economics & EVM:** Cost Baseline, облік праці через табелі (`WorkRecord`), накладні витрати (`ExpenseRecord`), аналіз освоєного обсягу (EVM: $PV, AC, EV, CPI, SPI$) та розрахунок прибутковості (P&L / TCO).
2. **Єдине сховище без фрагментації (All-in-PostgreSQL):**
   * Жодних окремих сторонніх баз даних (Neo4j, Milvus, Qdrant).
   * Реляційні сутності ядра, векторний семантичний пошук (`pgvector`), рекурсивні графи трасованості (`WITH RECURSIVE` + `CYCLE`) та ієрархічні матеріалізовані шляхи (`ltree`) функціонують у межах єдиної транзакційної моделі ACID.
3. **Семантична строгість моделі даних:**
   * Чітке розмежування **роботи (Work Item, зокрема Task)** та **керованих артефактів/доказів (Work Product)**.
   * Виконання задачі не є автоматичним схваленням результату (`Task.done != WP.approved`). Погодження артефакту спирається на незмінні ревізії, хеші (`payload_hash`), кворум та перевірку незалежності (SoD).
4. **Композитні документи (Специфікації вимог та тестів):**
   * Вимоги та тест-кейси є атомарними елементами з власними версіями та зв'язками, але об'єднуються в структуровані специфікації з незмінним маніфестом ревізій.
   * Повторне використання не клонує сутності й не розмиває авторство.
5. **Дворівневе модульне керування:**
   * Кожен проєкт містить обов'язковий кореневий документ `Generic Project Plan`.
   * Адміністратор керує глобальним каталогом модулів, а проєктний менеджер активує та налаштовує через чернетку плану лише релевантні методології та стандарти (Scrum, Waterfall, ASPICE 4.0, ISO 26262, ISO 21434).
6. **Автономність від систем зберігання коду (Repository & Tracker Independence):**
   * DELMOS не прив'язаний до єдиного вендора.
   * Підтримується вбудоване сховище (Internal DB/Git), чистий віддалений Git (SSH/HTTPS) та адаптери до GitLab, GitHub, Azure DevOps, Bitbucket, Forgejo/Gitea.

## 2. Структура репозиторію

```text
├── docs/                      # Повна технічна та нормативна документація
│   ├── README.md              # Карта та реєстр документів DELMOS
│   ├── requirements/          # Стейкхолдерські та системні вимоги (SHR, SWR)
│   │   ├── stakeholder/       # Вимоги стейкхолдерів (SHR-01..14)
│   │   └── software/          # Системні вимоги до підсистем (SWR-01..48)
│   ├── architecture/          # Архітектурні специфікації підсистем і моделей
│   │   ├── decisions/         # Архітектурні рішення (ADR-001..010)
│   │   └── gui/               # Core Web GUI, Guided UI та внески модулів
│   ├── specifications/        # SPEC-01..04 та CORE-CONTRACT-001 для першого зрізу
│   ├── memos/                 # Інженерні меморандуми та концепції (MEMO-001..004)
│   ├── use-cases/             # Базові ролі ядра й сценарії Admin/Project Manager
│   ├── testing/                # Стратегія тестування (V-модель)
│   ├── uat/                    # Приймальне тестування (UAT-001..004)
│   ├── operations/             # Runbook, резервне копіювання, DR, оновлення, логування
│   ├── security/                # Специфікація безпеки даних, секретів, вебхуків
│   ├── api/                     # Специфікація REST API
│   ├── compliance/              # Комплаєнс та мапування галузевих стандартів
│   ├── guides/                  # Бачення продукту, путівники розробника й користувача
│   ├── templates/               # Порожні шаблони ADR/SHR/SWR/MEMO/SPEC/UAT/Release Notes
│   ├── VERSIONING.md            # Політика семантичного версіонування
│   └── TRACEABILITY.md          # Агрегована матриця простежуваності SHR↔SWR↔ADR↔SPEC↔UAT
├── LICENSE                    # Ліцензія Apache 2.0
├── NOTICE                     # Повідомлення про авторські права
├── CONTRIBUTING.md            # Процес контриб'юції до проєкту
├── CODE_OF_CONDUCT.md         # Кодекс поведінки спільноти
├── SECURITY.md                # Політика повідомлення про вразливості
├── GOVERNANCE.md              # Модель прийняття рішень у проєкті
├── PORTING_PLAN.md            # Детальний план реалізації та перенесення дорожньої карти
└── README.md                  # Опис платформи
```
