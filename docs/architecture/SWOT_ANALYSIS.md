## 1. Вступ та контекст оцінки

Платформа **DELMOS** розробляється як автономна операційна система інженерного життєвого циклу (**ELM**) та проєктної економіки (**Project ERP / PPM**).

Базовий задум DELMOS сформовано на таких фундаментальних засадах:
1. **Повний інженерно-бізнесовий контур:** підтримується наскрізний цикл від Pre-sales/RFQ та R&D-досліджень до мультидисциплінарної розробки (HW + SW), контролю бюджету за стандартами фінансової звітності (CapEx проти OpEx) та сертифікаційного аудиту.
2. **Єдине сховище без фрагментації (All-in-PostgreSQL):** реляційні таблиці, графічні зв'язки (`WITH RECURSIVE` + `CYCLE`), матеріалізовані ієрархії (`ltree`) та векторний семантичний пошук (`pgvector`) функціонують у межах однієї транзакційної моделі ACID без сторонніх баз (Neo4j, Milvus).
3. **Семантична строгість моделі:** суворе розмежування діяльності (**Work Item, зокрема Task**) та результату (**Work Product**). Завершення завдання не є схваленням артефакту (`Task.done != WP.approved`).
4. **Композитні документи (Специфікації):** атомарні вимоги та тести мають власні ревізії, але об'єднуються у структуровані специфікації з незмінним маніфестом ревізій без дублювання тіл (SPEC-01..10).
5. **Автономність від сховищ (RepositoryProvider):** підтримка внутрішнього сховища (Internal DB/Git), чистого Git та корпоративних платформ (GitHub, GitLab, Azure DevOps, Bitbucket, Forgejo/Gitea).
6. **Нативна та легка архітектура:** єдиний Go-бінарник із вбудованим SPA (Vue 3, Pajamas tokens) під керуванням `systemd` на Ubuntu.

## 3. Детальний аналіз факторів

### 3.1. Strengths (Сильні сторони концепції)

1. **Єдина ACID-транзакційність та консолідована безпека:**
   * Усі операції — оновлення специфікацій, зміна зв'язків трасованості, розрахунок векторів та емісія подій через outbox — відбуваються в єдиній базі PostgreSQL.
   * Семантичний пошук та обхід графів поєднуються в єдиному SQL-запиті з фільтрами прав користувача (`project_id`, рівень допуску `classification`), виключаючи витік даних через сторонні бази.
2. **Семантична чистота інженерної моделі:**
   * Розмежування діяльності (Work Item) та результату (Work Product) усуває плутанину. Затвердження артефакту вимагає перевірки хешу (`payload_hash`), кворуму та правила незалежності рецензента (SoD).
3. **Гнучкість композитних документів (Специфікацій):**
   * Інженери працюють із вимогами як з атомарними об'єктами, але отримують цілісні специфікації з фіксацією точного маніфесту ревізій. Повторне використання вимог не створює копій.
4. **Повний інженерно-економічний контур:**
   * Поєднання інженерного життєвого циклу (ELM) та проєктної економіки (Project ERP / PPM): базові кошториси (`CostBaseline`), облік трудовитрат (`WorkRecord`), аналіз здобутої цінності ($PV, AC, EV, CPI, SPI$) та P&L.
5. **Мультипровайдерність сховищ:**
   * Можливість вибору сховища артефактів під час створення проєкту: від вбудованого збереження у внутрішній базі до корпоративних GitHub, GitLab чи Azure Repos.

### 3.2. Weaknesses (Слабкі сторони та проектні виклики)

1. **Навантаження на оперативну пам'ять (RAM):**
   * Індекси HNSW у `pgvector` вимагають утримання векторних графів у пам'яті. При сотнях тисяч вимог і тестів сервер БД вимагатиме суттєвого обсягу RAM (`shared_buffers`).
2. **Алгоритмічна складність ядра:**
   * Розрахунок детермінованих хешів композитних маніфестів, секундний планувальник, надійна черга з лізами (lease fencing) та контроль циклів графа потребують глибокого тестування багатопоточності.
3. **Обмеження зв'язки фронтенду з Pajamas:**
   * У дизайн-системі Pajamas відсутні готові компоненти для складної векторної графіки. Необхідно створити власні SVG-обгортки (на базі Vue Flow), узгоджені з токенами Pajamas.

### 3.3. Opportunities (Перспективи та зовнішні можливості)

1. **Витіснення застарілих легасі-монолітів:**
   * Siemens Polarion та IBM DOORS страждають від повільних інтерфейсів та складності адміністрування. DELMOS із нативною швидкістю Go, векторним пошуком та сучасним UI має високий ринковий потенціал.
2. **Інженерне AI-асистування нового рівня (Graph-RAG):**
   * Поєднання `pgvector` та нативного графа зв'язків уможливлює Graph-RAG: пошук суперечностей, підказка тест-кейсів до вимог (Smart Suggestion) без виходу за межі безпечного периметра компанії.
3. **Експансія в суміжні критичні галузі:**
   * Модульна природа каталогу дозволяє легко адаптувати систему для медичних виробів (IEC 62304), авіоніки (DO-178C) або залізничної автоматики (EN 50128) простим додаванням відповідних модулів.

### 3.4. Threats (Зовнішні загрози та ризики)

1. **Кваліфікація інструменту за ISO 26262 (Tool Qualification):**
   * Для проєктів рівня ASIL D вимагається формальна кваліфікація ПЗ за стандартом ISO 26262-8 (Розділ 11) із визначенням TCL (Tool Confidence Level). Необхідна завчасна розробка пакету Tool Qualification Kit.
2. **Конкурентний тиск із боку загальних платформ:**
   * GitLab та Jira можуть розширювати базовий функціонал вимог, тому DELMOS має чітко утримувати позиціонування саме як *оркестратора інженерних специфікацій, доказів безпеки та проєктної економіки*.

1. **SO (Зростання):** Позиціонувати DELMOS як швидку та надійну заміну важким інструментам минулого покоління завдяки єдиному бінарнику, простоті розгортання та унікальній функції Graph-RAG (дедуплікація та розумна трасованість).
2. **WO (Подолання слабкостей):** Партиціювати векторні таблиці та розраховувати ембедінги лише для ключових артефактів (вимог і тестів); для візуалізації стартувати з генерації Mermaid SVG із плавним переходом до інтерактивного полотна Vue Flow.
3. **ST (Захист від загроз):** Опиратися на незмінні ревізії з `payload_hash` та журнал погоджень SoD як головний козир при проходженні сертифікаційного аудиту ISO 26262 та ASPICE.
4. **WT (Мінімізація ризиків):** Формувати автоматизований валідаційний пакет (Tool Qualification Kit на базі `SPEC-01..10`, `VEC-01..03`, `GRP-01..03`) із перших релізів системи.
