# ADR-007: Транзакційна черга подій (Outbox), оренда повідомлень та секундний планувальник

- **Статус:** Прийнято (Accepted)
- **Дата:** 2026-09-23
- **Контекст:** Асинхронна автоматизація в інженерних системах (розрахунок ембедінгів, поширення прапорця підозрілості `is_suspect`, сповіщення, перерахунок метрик) вимагає надійної черги. Використання зовнішніх брокерів (RabbitMQ, Kafka, Redis) ускладнює нативне розгортання та створює проблему подвійного запису (Dual Write Problem), коли зміна в БД успішна, але публікація в брокер зазнала збою. Також потрібен розклад із точністю до секунди без дублювання запуску при перезапусках сервісу.
- **Рішення:** Реалізувати автоматизацію на базі PostgreSQL без сторонніх брокерів:
  1. *Патерн Transactional Outbox:* будь-яка подія ядра чи модуля записується в таблицю `event_outbox` у межах тієї ж SQL-транзакції, що й бізнес-зміна. Збій транзакції автоматично відкочує подію; успішний коміт гарантує її наявність.
  2. *Диспетчеризація та оренда (Lease Fencing):* фоновий диспетчер пробуджується через `LISTEN/NOTIFY` (або полінг) і створює записи доставки (`event_deliveries`) для кожної активної підписки. Воркери резервують повідомлення на фіксований час (`lease_until`) з унікальним маркером блокування.
  3. *Ідемпотентність доставки:* гарантія доставки як мінімум один раз (At-least-once) поєднується з фіксацією унікального `idempotency_key` на кожну дію обробника.
  4. *Секундний планувальник завдань:* підтримка розкладів `once`, `fixed_rate`, `fixed_delay`, `calendar` із точністю до секунди; фіксація настання завдання через таблицю `schedule_occurrences` із захистом від повторного виконання при рестартах.
- **Наслідки:**
  - *Позитивні:* Атомарність бізнес-зміни та enqueue у PostgreSQL усуває подвійний запис; сторонній брокер не потрібен. Повторна доставка вимагає ідемпотентності обробника та контролю оренди, а не гарантує exactly-once. Збереження аудиторського доказу й очищення черги визначені окремо в [ADR-010](ADR-010-audit-evidence-and-outbox-retention.md).
  - *Негативні / Компроміси:* Таблиці черги створюють навантаження на I/O бази даних; необхідність періодичної очистки (vacuum / partition retention) оброблених повідомлень.
