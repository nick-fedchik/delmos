# ADR-004: Дворівневе керування конфігурацією проєкту та обов'язковий Generic Project Plan

- **Статус:** Прийнято (Accepted)
- **Дата:** 2026-09-23
- **Контекст:** Проєкти в інженерних організаціях різняться за методологіями (Scrum, Waterfall, V-Model) та стандартами (ASPICE, ISO 26262, ISO 21434). Спроба «зашити» всі стандарти в ядро робить його перевантаженим, а надання проєкту повної свободи у встановленні неперевірених розширень несе ризики безпеки та розсинхронізації процесів підприємства.
- **Рішення:** Затвердити дворівневу архітектуру модульної конфігурації:
  1. **Кореневий інваріант:** кожен проєкт при створенні атомарно отримує головний конфігураційний документ — `Generic Project Plan` (`PLAN-001`, профіль `core:project_plan`) через зв'язок `ProjectPlanBinding`. Проєкт не може існувати без плану.
  2. **Рівень 1 (Системний адміністратор):** контроль глобального каталогу модулів інсталяції (`ModuleDefinition`, `ModuleRelease`). Адміністратор встановлює системну політику (`available`, `blocked_for_new_activation`, `suspended`).
  3. **Рівень 2 (Проєктний менеджер):** вибір модулів для конкретного проєкту здійснюється виключно в інтерфейсі редагування плану `PLAN-001` з-поміж дозволених адміністратором.
  4. **Контроль застосування (Plan Apply Pipeline):** будь-яка зміна конфігурації (активація модуля, зміна параметрів) є ревізією плану, проходить незалежне погодження та набуває чинності через команду `plan.apply`, яка атомарно оновлює робочі проекції в БД (`effective_plan_revision_id`, `config_generation`).
- **Наслідки:**
  - *Позитивні:* Відсутність «прихованих» конфігурацій; повна прозорість процесів для аудиторів; безпека інсталяції за збереження гнучкості проєкту.
  - *Негативні / Компроміси:* Зміна простого налаштування вимагає створення чернетки плану та проходження процедури погодження; потрібна валідація сумісності схем модулів до збереження.
