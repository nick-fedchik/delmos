# ADR-002: Суворе семантичне розмежування діяльності (WorkItem) та результату (WorkProduct)

- **Статус:** Прийнято (Accepted)
- **Дата:** 2026-09-23
- **Контекст:** У багатьох ALM/PMS системах (зокрема Siemens Polarion, Jira) використовується концепція універсального тікета (Work Item для задач, вимог, дефектів і тестів із єдиним статусом `open/done`). В інженерних галузях із високими вимогами до безпеки (ISO 26262, ASPICE) це призводить до змішування понять: закриття задачі розробником помилково сприймається як формальне схвалення інженерного артефакту, що є грубим порушенням процедур сертифікації.
- **Рішення:** Запровадити в DELMOS фундаментальне розмежування:
  1. `WorkItem` (Діяльність): завдання, баги, користувацькі історії. Має виконавця (`assignee`), часові оцінки та життєвий цикл виконання (`open -> in_progress -> done`).
  2. `WorkProduct` (Результат / Артефакт): керований інженерний об'єкт (вимога, архітектурний опис, тест-план, звіт, протокол). Має версії, незмінні ревізії, хеш вмісту (`payload_hash`), критерії повноти та аудиторський статус погодження (`draft -> in_review -> approved -> obsolete`).
  3. Інваріант: `Task.done != WP.approved`. Завершення завдання не змінює статус артефакту; затвердження ревізії артефакту вимагає перевірки хешу, кворуму та правила незалежності рецензента (Segregation of Duties).
  4. Зв'язок між роботою та артефактом реалізується як відношення багато-до-багатьох `WorkItemProductLink` із семантичними типами (`produces`, `updates`, `implements`, `verifies`, `reviews`).
- **Наслідки:**
  - *Позитивні:* Семантична чистота; унеможливлення підробки аудиторських доказів; чітке розділення відповідальності інженера та затверджувача.
  - *Негативні / Компроміси:* Необхідність двох окремих операцій при завершенні робіт (закрити таску та окремо подати ревізію на рецензію); дещо вищий поріг розуміння моделі для нових користувачів.
