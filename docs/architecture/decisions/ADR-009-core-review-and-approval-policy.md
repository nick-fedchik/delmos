# ADR-009: Незалежна рецензія та погодження точної ревізії ядра

- **Статус:** Прийнято (цільовий контракт, не реалізовано)
- **Дата:** 2026-09-23
- **Контекст:** Базовий [FSM Work Product](../WORK_PRODUCTS.md) розрізняє `draft`, `in_review`, `approved`, `obsolete`; [SHR-14](../../requirements/stakeholder/SHR-14-core-access-and-assurance.md) і [SWR-45..46](../../requirements/software/SWR-10-core-access-assurance.md) вимагають незалежних рішень. Назви ролей не визначали мінімальний кворум, а діаграма плану змішувала відмову рецензента з технічним конфліктом версій.
- **Рішення:** Для початкового Core workflow діяти так:
  1. `wp.submit` створює ReviewRequest на точний `revision_id`/`payload_hash` і переводить WP у `in_review`. Reviewer і Approver мають явні дійсні RoleBindings у scope та призначення на ReviewRequest; System Administrator або окремо делегований власник `access.grant` надає RoleBinding. Project Manager може запропонувати кандидата з уже наявним правом, але не створює собі право чи незалежність через власну пропозицію.
  2. Один позитивний `wp.review` незалежної від автора особи є передумовою; він фіксує власний незмінний запис, не змінюючи WP на `approved`. Для базового кворуму потрібен один `wp.approve` незалежної від автора особи на ту саму ревізію і хеш. Reviewer та Approver можуть бути однією особою, лише якщо вона має **обидва** окремі дозволи, обидва призначення, і не є автором; кожне рішення фіксується окремо. Модуль може вимагати суворішого кворуму, але не слабшого.
  3. Reviewer або Approver із дозволом `wp.request_changes` може повернути об'єкт до `draft`, записавши причину. Це висновок «потрібні зміни», не новий стан WP `rejected`. Створення наступної ревізії потребує нового ReviewRequest; старі рішення ніколи не переносяться на новий хеш.
  4. Сервер атомарно перевіряє актуальність ревізії, `row_version`, scope, стан, право, призначення, SoD і кворум перед зміною стану. Повтор із тим самим ключем операції повертає попередній результат; інша конкурентна дія повертає конфлікт без другого підпису. Невідомий/невидимий об'єкт не розкривається; 403 означає відсутність дозволу на видиму дію, 409 — зміну версії, 422 — невиконаний інваріант для авторизованого запиту.
  5. План є WP і погоджується за тією самою процедурою через `plan.approve` на точний хеш; **лише після цього** користувач з окремим `plan.apply` атомарно оновлює `effective_plan_revision_id`. Виняток з правила (Waiver) проходить окрему команду й право. Для підпису зберігати мінімально необхідні actor/scope/time/revision/hash/correlation без сирих секретів.
- **Альтернативи:** Один клік «схвалити» без Review відхилено через ризик неперевіреної ревізії; окрема роль Reviewer *завжди* відмінна від Approver відкладена до стандарту/проєкту, бо Core достатньо незалежності від автора та окремих дозволів; окремий статус `rejected` відхилено на користь наявного переходу `in_review → draft` із мотивованим записом.
- **Наслідки:** Потрібні два незмінні записи рішення і контракт призначення ReviewRequest; UI не може обходити заборону підтвердженням. Архівування артефакту не стирає історію Review/Approval. Мінімальний кворум дозволяє малому проєкту працювати без обов'язкових трьох різних осіб, але ніколи без незалежного від автора погоджувача.
- **Верифікація:** [UAT-004](../../uat/UAT-004-core-roles-review-approval.md), негативні серверні тести самопогодження, застарілого хешу, подвійного запиту, відкликаного RoleBinding та переходу без позитивної рецензії.
