## Як користуватися реєстром

«Задекларовано» означає, що архітектура або ADR вже обрали напрямок, **не** що він реалізований чи пройшов тест. «Кандидат» потребує сценарію, експерименту та за потреби ADR до зміни публічного контракту. Не обирати шаблон лише тому, що він популярний: для кожного потрібні конкретна проблема, межа застосування і дешевий тест, який може спростувати вибір.

| Шаблон і статус | Де потрібний | Як не зловживати / перевірити |
| --- | --- | --- |
| **Модульний моноліт + ports/adapters** — задекларовано в [ARCHITECTURE.md](ARCHITECTURE.md) | Доменні use cases незалежні від HTTP, pgx, GUI й зовнішніх SDK. Один бінарник, ізольовані модулі; адаптери лише на краях. | Не плутати з плагінами довільного коду чи окремими мікросервісами. Compile/import-тести на напрямок залежностей; замінити Git-адаптер тестовим без змін домену. |
| **Aggregate/transaction boundary** — правило в [guardrails](IMPLEMENTATION_GUARDRAILS.md) | Проєкт+обов'язковий план, WP+ревізія, погодження точного хешу; один власник запису і явні інваріанти. | Не робити «один aggregate для всього проєкту». Тест атомарного rollback і конкурентних змін `row_version`. |
| **Immutable revision / snapshot / composition** — [ADR-002](decisions/ADR-002-strict-workitem-workproduct-separation.md), [ADR-003](decisions/ADR-003-composite-specification-manifests.md) | Відтворення історії артефакту й складу специфікації на точну дату/ревізію; бейзлайн як незмінний знімок. | Це **не повне event sourcing**; поточний стан і незмінні ревізії мають різну роль. Перевірити повторне обчислення хешу, відтворення бейзлайну після наступної редакції. |

| **Read projections / CQRS-lite** — кандидат | Відновлювані пошук, матриця RTM, економічні агрегати та UI-списки без write-through до чужих агрегатів. | Не створювати друге первинне сховище чи загальний event store. ## Не закладати без окремого рішення

Мікросервіси та розподілену транзакцію; повне event sourcing; окремі graph/vector сервери; довільне завантаження виконуваних плагінів; клієнт як джерело прав; автоматичне схвалення артефакту після закриття задачі; synchronous виклик зовнішнього API всередині транзакції; «exactly-once» без доказу. Ці підходи несумісні з поточними інваріантами або додають витрати без підтвердженої потреби. Якщо вимога зміниться — спочатку SHR/SWR, альтернативи та новий ADR.

## Рішення, які ще слід оформити

1. Рішення про retention/FK прийнято в [ADR-010](decisions/ADR-010-audit-evidence-and-outbox-retention.md); перед production лишається затвердити інсталяційні строки, legal hold, відновлення й підтвердити SQL-поведінку тестами.
2. Чи потрібна окрема read projection для конкретного виміряного вузького місця та який допустимий lag; до вимірювання використовувати простий SQL.
3. Матриця версій API, конвертів подій, JSON Schema і модулів: підтримка старих клієнтів/схем, порядок rollout, правила deprecation.
4. Хто володіє типами імпорту/експорту і гарантує redaction та походження доказів через усі адаптери.

Це **кандидати на майбутні ADR**, а не нові прийняті рішення; запис створюється за [шаблоном ADR](../templates/ADR-TEMPLATE.md) після отримання перевірних фактів. Порівняння контентних і проєктних шаблонів залишено в [CONTENT_PROJECT_PATTERNS.md](CONTENT_PROJECT_PATTERNS.md), щоб не дублювати його таблиці.
