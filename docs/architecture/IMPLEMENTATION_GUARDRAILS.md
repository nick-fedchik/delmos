## Власність і межа команди

| Область | Хто змінює стан | Правило до початку кодування |
| --- | --- | --- |
| Проєкт і прив'язка плану | Core Project/Plan | Створення проєкту й обов'язкового плану атомарне; застосування плану — окрема команда з погодженням. |
| Work Product і ревізії | Core Work Products | Зміна створює нову ревізію; модуль додає профіль/схему, але не пише базові колонки або затвердження в обхід Core. |
| Права і рішення | Core Access/Review | SoD, дозволи й аудит перевіряються сервером у кожній команді, не в UI чи коді модуля на віру. |
| Трасованість і бейзлайн | Core Trace/Baseline | Зв'язок і бейзлайн посилаються на точні дозволені ревізії; міжконтекстні посилання не дають права читання. |
| Проєкції та автоматизація | Власний модуль/воркер | Інша область не змінює чужі первинні записи напряму; доставка подій повторювана та ідемпотентна. |

Це робочий кордон відповідальності, а не нова схема БД. Якщо дві області мають одночасно міняти один первинний запис, перед реалізацією слід визначити одну команду-власника, транзакцію і компенсацію для зовнішнього ефекту.

## Залежності та запис

`HTTP/UI -> application use case -> domain/ports -> adapters` є напрямком залежностей у коді; Go-домен не імпортує HTTP, pgx, SDK провайдерів чи компоненти UI. Зовнішнє сховище коду підключається через [RepositoryProvider](../specifications/SPEC-02-REPOSITORY-PROVIDER-INTERFACE.md); адаптер перекладає чужі помилки й ідентифікатори на внутрішні, не стає власником бізнес-правил. Модулі реєструють внески через [типізовані провайдери](MODULES.md), а не змінюють чужі таблиці й ендпоінти обхідними імпортами.

Одна синхронна команда: ідентифікує актора/проєкт, перевіряє серверні права і версію стану, застосовує інваріанти, у тій самій транзакції записує доменний стан та outbox-подію, повертає ревізію або структуровану помилку. Ніяких мережевих викликів усередині транзакції БД; зовнішні ефекти й довгі розрахунки — після commit через outbox, із повторною перевіркою права/класифікації на момент фактичної доставки. Технічна ідемпотентність не означає, що небезпечна дія дозволена: повторне `approve/apply/freeze` має повертати той самий результат або конфлікт, а не дублювати рішення.

Читання використовує проєкції/індекси для швидкості, але вони відновлювані з первинних записів, не є паралельним джерелом істини. Якщо індекс/семантичний вектор застарів, показати це й обмежити результат, не видавати його за актуальний доказ. Кожен запит з фільтрацією по проєкту, ролі та `classification` проходить перевірку доступу *до* повернення метаданих, графа, вектора чи експорту.

## Еволюція контрактів і схеми

Для публічних API перед реалізацією вести машинозчитуваний OpenAPI-контракт і [людиночитну специфікацію](../api/API_SPECIFICATION.md) в одному перегляді; однакові помилки 401/403/404/409/422 перевіряються контрактними тестами. Додавання необов'язкового поля допустиме лише за визначених default/nullable і поведінки старого клієнта; зміна семантики, вилучення поля та повторне використання старого enum-значення вимагають окремого рішення про версію і міграцію споживачів.

Подія має `event_key`, `schema_version`, `event_id`, `correlation_id` і [конверт SPEC-04](../specifications/SPEC-04-EVENTS-TRIGGERS-RULES-ENGINE.md); споживач має tolerувати підтримувані невідомі необов'язкові поля, але не невідомий несумісний major schema version. Outbox гарантує at-least-once, не exactly-once: обробник зберігає ключ обробленого ефекту, застосовує lease fencing і не віддає `delivered` до стійкого запису результату. Під час повтору/відновлення тестувати crash між commit стану, outbox, зовнішнім викликом та ACK.

Міграції [forward-only із SHA-256 та advisory lock](../requirements/SYSTEM_REQUIREMENTS.md); старі файли не редагуються. Для зміни на живих даних спочатку спланувати expand -> backfill/verification -> перехід читання/запису -> contract у майбутній версії, **якщо** обіцяється співіснування версій. Наразі [runbook оновлення](../operations/UPGRADE_AND_ROLLBACK.md) вимагає вікно обслуговування і backup/restore; zero-downtime та запуск старого бінарника на новій схемі не заявляються без окремо доведеної сумісності.

## Рішення до першої реалізації

1. Архітектурний конфлікт retention/видалення вирішено [ADR-010](decisions/ADR-010-audit-evidence-and-outbox-retention.md): історичні докази і `audit_events` незмінні; приклад DDL у [SPEC-04](../specifications/SPEC-04-EVENTS-TRIGGERS-RULES-ENGINE.md) більше не каскадує від проєкту до outbox і від outbox до delivery. До першої production-очистки лишається затвердити строк зберігання, legal hold і перевірити FK/backup на реальній БД.
2. Для кожного use case, який охоплює дві області, зафіксувати власника транзакції, постумови, подію, ідемпотентність та поведінку при повторі/частковій відмові. Не починати DDL, якщо неясно, хто має право змінювати первинний стан.
3. Для API, подій, схем модулів і JSON Schema визначити підтримувані версії клієнта/сервера, період співіснування й процедуру відмови від старої версії. Відкритий вибір оформляється новим [ADR за шаблоном](../templates/ADR-TEMPLATE.md), а не позначається як уже ухвалений.

Це не переписує [чинні ADR](decisions/README.md); вони є джерелом прийнятих рішень. Перевірка того, що правила можна реалізувати, — один наскрізний вертикальний зріз: створення проєкту з планом, чернетка WP, нова ревізія, зв'язок, погодження, подія та адресне читання з перевіркою прав.
