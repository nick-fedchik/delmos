## 1. Стан кожного маршруту

| Стан | Що користувач бачить | Дія |
| --- | --- | --- |
| `loading` | Скелет структури того самого екрана або індикатор завантаження з назвою дії; без стрибка висоти | Не показувати «порожньо» до завершення запиту. |
| `ready` | Дані, актуальний час/версія, дії згідно з правами | Для довгих фонових дій показати `queued/running/completed/failed` біля об'єкта. |
| `empty-unconfigured` | Для чого функція потрібна, що потрібно налаштувати, одна основна дія | За відсутності права налаштування — пояснення і маршрут до відповідальної ролі. |
| `empty-no-data` | Як створити перший запис і що з'явиться потім | Не повторювати основну дію одночасно у хедері й порожньому стані. |
| `empty-filtered` | «Нічого не знайдено» з можливістю змінити/скинути фільтри | Не закликати створити дані, які вже існують поза фільтром. |
| `forbidden` | «Недостатньо прав для цієї дії», без розкриття прихованих даних | Не пропонувати дію, яка все одно поверне 403; пояснити, кому звернутися. |
| `error` | Що не вдалося, чи збережені зміни, причина якщо відома, кнопка повторити безпечну операцію | Тривалий стан; не лише toast і не сирий HTTP-код. |
| `degraded` | Яка зовнішня можливість недоступна і що продовжує працювати локально | Дозволити автономні дії; повтор із backoff. |

Усі стани мають текстовий сигнал, доступний screen reader; один лише колір або іконка недостатні. Немає нескінченного `loading` без тайм-ауту чи шляху повтору. Запит, що вже змінив стан, не повторюється автоматично без ідемпотентності.

## 2. Яке повідомлення куди спрямувати

| Ситуація | Поверхня | Не робити |
| --- | --- | --- |
| Результат уже видно на сторінці | Inline-стан поруч із об'єктом | Додатковий toast «Збережено». |
| Коротке підтвердження, результат не видно | Тимчасовий toast без кнопок | Вбудовувати «Скасувати» чи «Переглянути» в auto-dismiss. |
| Важлива помилка, що вимагає дії | Inline alert біля форми/сервісу, видимий до усунення | Автоматично прибирати або ховати за лічильником нижнього бара. |
| Довга задача чи доставка події | Постійний стан job/record, власна адреса; за потреби сповіщення про завершення | Обіцяти завершення після прийняття в чергу. |
| Потрібна увага пізніше | Центр сповіщень з непрочитаними подіями і посиланням на об'єкт | Ототожнювати сповіщення з історичним журналом аудиту. |
| Критичний стан усієї інсталяції | Строгий статус системи та шлях до діагностики | Показувати кожен збій зовнішньої інтеграції як недоступність ядра. |

Сповіщення зберігає тип події, час, стан `unread/read`, адресу ресурсу й причину, доступну користувачу. Немає доступу до ресурсу — немає його вмісту в заголовку/preview. Верхній індикатор — лічильник непрочитаних; нижній — агреговані помилки поточної сторінки. Toast зникає, але повідомлення, що вимагає роботи, лишається доступним у записі або центрі сповіщень. Пауза авто-закриття на hover/focus і ручне закриття корисні для коротких toast, але не замінюють доступний постійний стан.

## 3. Редагування і незбережені зміни

Редагування керованого артефакту — явне збереження чернетки; зміна не означає погодження. Панель дій показує `Є незбережені зміни`, збереження/скасування й поточний результат. Візуальна зміна кнопки — лише додаткова ознака, без нескінченної пульсації та з повагою до `prefers-reduced-motion`. На маршрутний вихід з брудної форми запропонувати **«Зберегти», «Не зберігати й вийти», «Продовжити редагування»**; при помилці збереження лишитися на сторінці, показати помилку й не втратити введене. При закритті вкладки — нативне попередження браузера.

Автозбереження — лише для незалежних безпечних полів та чернеток, якщо це явно показано (`Зберігається...`, `Чернетку збережено`, час). Не автозберігати цілий план, права, секрети, конфіденційність, бюджет, `plan.approve`, `plan.apply`, `wp.approve` чи бейзлайн. Конфлікт версій (`row_version`) не можна перезаписувати мовчки: показати різницю, авторів, час і можливість відновити чернетку. Після збереження дати стабільну адресу нової ревізії.

## 4. Підтвердження і незалежність

| Дія | Перед виконанням | Після виконання |
| --- | --- | --- |
| `wp.submit` | Показати конкретні порушені поля/правила з якорями, не фальшиве «Готово». | Стан `in_review`, наступний крок рецензента. |
| `wp.approve`, Gate Review | Серверна перевірка прав, кворуму, незалежності та exact revision hash; inline причина вето. | Незаперечний запис рішення і посилання на докази. |
| `plan.apply` | Порівняння чернетки з поточною конфігурацією, показ впливу й обов'язкове погодження. | Яку конфігурацію застосовано і які перевірки увімкнено. |
| `baseline.freeze` | Перелік включених ревізій, відсутніх доказів та наслідки незмінності. | Адреса створеного бейзлайну, не лише сповіщення. |
| Руйнівна дія | Окреме підтвердження з назвою об'єкта й наслідками; серверна перевірка повторно. | Повернення до безпечного маршруту, залишення доказів згідно з retention. |

Особливо: попередження про конфлікт SoD **не є запитом на підтвердження обходу**. Клієнт може пояснити заборону, але ніколи не перетворює `veto` на `success` діалогом або прапорцем. Виняток (`Waiver`) — окремий підписаний workflow з дозволами й аудитом, а не `confirm()`.

## 5. Перевірка

Тести мають відрізняти порожню базу від порожнього пошуку; зберігати введене після timeout; утримувати alert до вирішення; не лишати помилку тільки у toast; перевіряти hover, клавіатуру й screen reader; дублювання фонового job не створює новий запис; статус `queued` не повідомляє про `completed`; серверне 403/422 та SoD-блокування не можна обійти UI; після зміни прав застарілий CTA зникає/пояснюється без витоку змісту.
