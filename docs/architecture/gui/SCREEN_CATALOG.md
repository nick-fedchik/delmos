## 1. Базові екрани Core GUI

Core володіє оглядом системи/програми/проєкту, створенням проєкту та обов'язкового `PLAN-001`, роботою з `WorkItem`, базовим редактором і переглядом `WorkProduct`/ревізій, контролем прав і налаштувань, довідкою, системною діагностикою. Типи `plan`, `requirement`, `architecture`, `test_spec`, `report`, `record` використовують спільні компоненти полів, workflow, статусу, коментарів і адресних посилань. Модулі можуть додавати профілі й секції, не форкнувши ці сторінки. Докладніше: [каталог сутностей](../ENTITY_CATALOG.md), [сценарії користувачів](../../use-cases/PROJECT_MANAGER.md).

## 2. Матриця всіх спеціалізованих сценаріїв

Колонка «Вхідний шаблон» називає досліджений файл з ідеєю екрана; це не адреса у DELMOS і не обіцянка вже готової реалізації.

| Вхідний шаблон | Власник DELMOS | Що зберегти | Керований контекст та адаптація |
| --- | --- | --- | --- |
| `requirement-edit-form.md` | Core `WorkProduct` + активні профілі вимог | Типізовані enum/boolean/long-text поля, валідація, захист незбереженого | Пояснити, навіщо потрібні критерій приймання та спосіб перевірки; модуль визначає застосовні поля за схемою, не жорсткий перелік усіх стандартів; `wp.submit` окремо від save. |
| `requirement-list-filters.md` | Core списки + загальний filter pattern | Фільтри, сортування, `query` у URL, відновлення після reload/back | Показати кількість збігів, очищення фільтрів, окремий стан «немає збігів»; галузеві фільтри лише після активації модуля. |
| `rtm-by-role.md` | `tooling.rtm_matrix` (горизонтальний) | Групування `TraceLink` за роллю, число зв'язків, деталізація, CSV | Пояснити, що доводить кожен тип зв'язку і як виправити `suspect`; дозволи перевіряти для обох кінців; перелік ролей із версійованого реєстру, CSV лише для дозволеного набору з redaction. |
| `test-management.md` | `tooling.test_execution` + Core `test_spec` | Список, деталь/редактор, запуск і результат (`pass/fail/not_run`) | Розділити версійований тестовий опис і фактичний запуск; показати передумови, пов'язані вимоги, точну ревізію, висновок і наступний крок при failed. |
| `coverage-dashboard.md` | `tooling.rtm_matrix` + `MetricProvider` | Динаміка покриття, лінія цілі, сегментація | Пояснити знаменник, часовий діапазон, джерело/свіжість і поріг; графік разом з таблицею та станом «немає вимірювань», експорт перевірити на витік даних. |
| `release-planning.md` | Планування проєкту / майбутній горизонтальний release capability | Версії, planned/actual milestones, Gantt і посилання на SBOM | Пояснити, які віхи/докази потрібні перед публікацією; розрізняти planned/actual, затвердження і заморожений бейзлайн. Не створювати друге джерело істини для `Milestone`. |
| `scorecard-editor.md` | Планований модуль якості / `compliance.aspice` за контекстом | Критерії, оцінки, примітки і підпис окремих рядків | Пояснити шкалу і доказ для оцінки; signoff — серверна команда з незалежністю й записом рішення, не локальний прапорець `signedOff` до save. |
| `action-request-list.md` | `compliance.iso26262`/модуль якості, якщо активований | Запити дій, терміни, severity, фільтри, CSV | Показати причину запиту, виконавця, строк, наступну відповідальну дію; «прострочено» за часовою зоною/правилом, не лише кольором. |
| `asil-distribution.md` | `compliance.iso26262` | Розподіл ASIL і таблиця декомпозиції, можливість експорту | Пояснити джерело і обмеження класифікації; QM/A-D із текстом/легендою, не фіксований hex; експорт з назвою проєкту, датою та доступними доказами. |
| `confirmation-planning.md` | `compliance.iso26262` | План незалежних підтверджень, дата, рецензент, статус | Показати передумови незалежності до спроби підпису; не дозволяти `confirm()` обійти SoD, рішення фіксується сервером на точній ревізії. |
| `overdue-confirmation-widget.md` | `compliance.iso26262` (внесок до огляду Core) | Агрегат прострочених підтверджень з переходом до записів | Віджет існує лише за активним модулем; показати число, зрозумілий часовий критерій, посилання на запис і доступну дію, не окрему копію workflow. |
| `aspice-capability-radar.md` | `compliance.aspice` | Порівняння цільових і досягнутих capability levels, деталі процесу | Пояснити одиниці і як сформовано оцінку; осі із застосованої версії процесного каталогу, не жорстко 14; таблиця з числовими даними й легендою поруч із графіком. |
| `aspice-pa-detail.md` | `compliance.aspice` | Practice-by-practice evidence/gaps, фільтрація | Геп містить порушену практику, доказ і доречну наступну дію; не називати практику «досягнутою» лише тому, що є заповнене поле. |
| `tara-workspace.md` | `compliance.iso21434` | Сценарії загроз, CWE, зв'язки до заходів пом'якшення | Дві адресні вкладки, ризик із текстовим рівнем/причиною; показати джерело CWE, ризик до/після контролю, пов'язаний артефакт і наступний крок оцінки. |

## 3. Екранні шаблони й компоненти

| Повторюваний шаблон | Core забезпечує | Модуль додає |
| --- | --- | --- |
| Список / таблиця | Пошук, URL-фільтри, порожній стан, pagination, адресні рядки, право експорту | Типи фільтрів, колонки, значення й дії за дозволами. |
| Деталі / редагування | Ревізія, status, schema validation, dirty guard, SoD, breadcrumbs, help | Поля/схеми, специфічні передумови, профіль/правило переходу. |
| Dashboard / chart | Фільтри дат, пояснення джерела і доступності, таблиця альтернативних даних | Розрахунок, поріг, метрика, контекстний drill-down. |
| Підпис / Gate Review | Серверне рішення, audit, exact revision, заборони й waiver-workflow | Тип доказу, критерій оцінки, незалежність за стандартом. |

**Навігація:** горизонтальні екрани з'являються у відповідних групах роботи/перевірки, галузеві — у розділі активованого стандарту; віджет має адресу на повний екран. Кожен екран потребує власного `routeKey`, станів [loading/empty/error](STATES_AND_FEEDBACK.md), inline-пояснення мети, офлайн-довідки та перевірки доступу. Майбутні домени з [реєстру комплаєнсу](../../compliance/domains/README.md) використовують той самий контракт; створення окремого файлу домену не означає наявність його Web GUI.
