## 1. Власність і вибір елемента

Перш ніж створювати компонент, перевірити актуальний UX-патерн Pajamas, чи експортований компонент у вибраній версії `@gitlab/ui`, і чи працює його API у Vue 3 DELMOS. Якщо ні — створити адаптер із тим самим доступним контрактом; не копіювати CSS/DOM стороннього компонента в кожен модуль. Core GUI володіє наведеними нижче складеними елементами; модулі надають дані, підписи й правила тільки через [контракт внесків](MODULE_UI_CONTRIBUTIONS.md). Назви в таблицях — **ролі елементів**, не оголошені TypeScript-експорти.

| Елемент Core GUI | Призначення | Договір зі сторінкою / модулем |
| --- | --- | --- |
| Контекстний верхній бар | Назва продукту, контекст, пошук, стан, меню користувача | Breadcrumb/назва, дозвіл на пошук, короткий агрегований стан; модуль не додає власний бар. |
| Бічна навігація | Перехід між програмою, проєктом і активними модулями | Унікальний route key, короткий перекладений підпис, потрібне право, parent group (до двох рівнів). |
| Контекстна права панель | Офлайн-довідка і, за наявності, окремий режим асистента | Тема довідки, дозволені джерела, поточний `routeKey`/об'єкт; обов'язкова допомога не залежить від AI. |
| Нижній статус-бар | Версія, діагностика сторінки, допомога зі скороченнями | Лічильник невирішених проблем із шляхом до них; копіювати тільки очищений support-контекст. |
| Заголовок сторінки та панель дій | Breadcrumb, назва, статус, одна primary action, збереження | Назва дії від результату; sticky-панель не перекриває останнє поле і відображає dirty/saving/failed. |
| Керований блок передумов | Показати чому дію не можна почати і як усунути причину | Причина від сервера, потрібна роль/стан, безпечний маршрут; не дублювати звичайний опис сторінки. |
| Список і таблиця | Пошук, фільтри/сортування, адресні записи | Query-параметри відтворюють стан; альтернативи для вузького екрана; права на експорт окремі від прав читання. |
| Редактор артефакту | Форма + схеми модулів + ревізії | Label, необов'язковий пояснювальний текст, пов'язана помилка й фокус; `save` відмінне від `submit/approve`. |
| Індикатор стану / бейдж | Помітний системний статус або ризик | Текстовий статус і семантична роль; не прикрашати кожне метаполе бейджем. Користувацька категорія — мітка, не статус. |
| Стан порожнього вмісту | Відсутність даних, конфігурації або збігів пошуку | Різні тексти/дії за станом, один доступний primary CTA, аналітика без вмісту користувача. |
| Повідомлення та сповіщення | Результат дії, блокування, асинхронна подія | Inline для видимого результату, постійний alert для відмови, toast лише для короткого підтвердження без дії. |
| Візуалізація доказів | RTM, граф, метрики, пороги й drill-down | Підпис джерела/одиниць/свіжості, легенда + таблиця даних, доступні посилання на ревізії. |

## 2. Становий контракт

Для кожного елемента, який читає або змінює дані, описати `loading`, `ready`, `empty`, `error`, `forbidden`, `degraded` там, де це має сенс; для команд додати `idle`, `dirty`, `saving`, `saved`, `failed`, `conflict` і повтор без подвійної мутації. Не показувати «порожньо» до завершення завантаження; не повідомляти `approved` до серверного підтвердження; після 403 приховати чутливі дані; після 409 зберегти введене для вирішення конфлікту. Поведінка й копірайт цих станів визначені у [STATES_AND_FEEDBACK.md](STATES_AND_FEEDBACK.md).

Сенсорні цілі, порядок Tab, видимий фокус, клавіатурна активація і повернення фокусу після закриття панелі — частина контракту, не окремий косметичний тест. Для значків статусу є текстова назва, для неочевидних іконок дії — tooltip із назвою; іконка не замінює текст ризику чи критичного підтвердження. Іконки беруться з перевіреного каталогу, власний знак продукту визначає [BRANDING.md](BRANDING.md).

## 3. Пакет документації кожного складеного елемента

Дизайнер і розробник разом фіксують: ціль і «коли не використовувати»; автора/власника; вхідні дані й права; анатомію; варіанти та стани; поведінку миші/дотику/клавіатури; light/dark/forced-colors/reduced-motion; мобільне перепакування; приклади реальних текстів `uk-UA` і `en-US`; порожній/помилковий стан; критерії візуальних і функціональних тестів. Компонент без цих даних не вважається готовим до повторного використання модулем.

Для важливих робочих поверхонь потрібні story/examples зі станами й автоматизовані тести поведінки. Не потрібно створювати окрему абстракцію лише через однакове оформлення двох сторінок: спільний компонент має прибирати повторення логіки, доступності або контракту станів.
