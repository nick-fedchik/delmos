## 1. Актори та межі повноважень

| Актор | Відповідальність у DELMOS | Чого НЕ отримує автоматично |
| --- | --- | --- |
| **System Administrator** | Глобальна конфігурація системи, керування користувачами, політиками доступу, каталогом модулів, підключеннями сховищ та аудитом безпеки. | Право авторства та затвердження інженерних специфікацій і цілей безпеки конкретних проєктів. |
| **Host Operator / DBA** | Налаштування операційної системи Ubuntu 26.04, служби `delmos.service`, нативного PostgreSQL, резервне копіювання (`pg_dump`) та встановлення розширення `pgvector`. | Прикладну сесію адміністратора або роль інженерного затверджувача (Safety Approver). |
| **Project / Programme Manager** | Склад проєкту чи програми, активація дозволених модулів через план, планування ресурсів та бюджету. | Доступ до системного командного рядка (OS Shell), відкритих секретів сховищ та глобальних налаштувань. |
| **Auditor** | Доступ до журналів аудиту, незмінних ревізій, матриць трасованості та бейзлайнів у режимі «лише для читання». | Право внесення змін до документів, налаштувань чи відкликання сесій. |
| **Service Principal** | Технічний доступ автоматизації (CI/CD, фонові воркери) за підписаним контрактом токена. | Привілеї звичайного користувача чи інтерактивний вхід до вебпанелі. |

Для ядра першочергові bootstrap, сесія, явний RoleBinding, здоров'я сервісу та резервне копіювання (`ADM-001..003`, `ADM-005..007`, `ADM-013..015` у міру появи даних). `ADM-004`, зовнішні провайдери (`ADM-008..009`) та політики майбутніх модулів (`ADM-010`) належать наступним етапам, а не передумовам першого сценарію. Сценарії інших базових ролей — у [каталозі Core](README.md); доступ Host Operator до ОС не надає йому прикладних ролей.

| **ADM-013** | Діагностика здоров'я ядра (/healthz, /readyz) | System Administrator / `health.read` | Перевірка працездатності процесу та доступності бази даних ядра |
| **ADM-014** | Аудит безпеки та експорт діагностичних логів | System Administrator або Auditor / `audit.read` | Незмінний журнал дій із цензуруванням секретів і паролів |

## 3. Ключові операційні сценарії

### Сценарій 1: Резервне копіювання та верифікація відновлення (ADM-015)
1. Host Operator запускає процедуру створення резервної копії через нативний скрипт чи Makefile.
2. Система створює кастомний дамп PostgreSQL, що включає всі реляційні таблиці, зв'язки трасованості та вектори `pgvector`.
3. Автоматично генерується файл контрольної суми `sha256sum`.
4. Для верифікації надійності запускається тестове відновлення (`restore-check`) у тимчасову ізольовану БД під керуванням окремого процесу.
5. Перевіряється цілісність таблиць, кількість ревізій та успішність читання бейзлайнів; після цього тимчасова БД безпечно видаляється.

### Сценарій 2: Безпечне підключення провайдера репозиторію (ADM-008, ADM-009)
1. Системний адміністратор відкриває розділ підключень сховищ і обирає тип провайдера (`Internal`, `Plain Git`, `GitHub`, `GitLab`, `Azure Repos`, `Bitbucket`, `Gitea`).
2. Вказується адреса ендпоінту та у захищене write-only поле вводиться токен або SSH-ключ.
3. Система виконує неруйнівну діагностичну пробу (probe): перевіряє доступність сервера, валідність TLS-сертифіката та наявність необхідних інженерних прав (читання репозиторію, створення гілок).
4. За успішного результату проби створюється сутність `RepositoryBinding`; відкритий секрет ніколи не відображається в інтерфейсі повторно і не записується у відкриті логи.

### Сценарій 3: Аварійне призупинення модуля (Emergency Suspend, ADM-010)
1. У випадку виявлення критичного дефекту в логіці галузевого розширення адміністратор встановлює для нього політику `suspended`.
2. Система негайно блокує виконання правил цього модуля в усіх активних проєктах; спроби затвердити артефакти, залежні від цих правил, отримують обґрунтоване блокування `blocked / degraded`.
3. Дія не видаляє дані чи налаштування в проєктних планах; факт призупинення та причини детально фіксуються в журналі аудиту безпеки.
