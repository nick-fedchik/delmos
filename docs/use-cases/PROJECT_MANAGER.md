## 1. Актор та роль у системі

| Актор | Призначення та межі повноважень |
| --- | --- |
| **Project Manager (PM)** | Відповідає за повний цикл проєкту: від оцінки пропозицій (Pre-sales) та R&D до системної розробки (HW/SW), вибору методологій, забезпечення стандартів (ASPICE, ISO 26262), контролю ресурсів і базового кошторису (EVM, P&L). |
| **Дозволені дії** | Редагування та подання проєкту плану `PLAN-001`, вибір та налаштування модулів із дозволеного каталогу, налаштування фаз, віх і бюджетних лімітів, проведення Gate Reviews, публікація бейзлайнів. |
| **Заборонені дії** | Не має права змінювати глобальні політики системи, самостійно призначати собі ролі незалежного асесора з безпеки (SoD) або обходити блокуючі правила валідації інваріантів (Veto). |

Базовий зріз ядра: `PM-001`, внутрішнє сховище в `PM-002`, `PM-003`, `PM-013` та застосування **вже незалежно погодженого** плану в `PM-014` за окремим дозволом `plan.apply`. Зовнішні провайдери, методології/стандарти (`PM-004..007`), економіка й ресурси (`PM-011..012`, `PM-017`) — цільові сценарії наступних етапів, не передумова P1/P2. Інші планувальні дії вводяться за [дорожньою картою](../architecture/ROADMAP.md). Назва ролі PM не є автоматичною видачею всіх перелічених дозволів.

## 2. Каталог сценаріїв використання (Use Cases)

| ID | Назва сценарію | Основна дія | Результат |
| --- | --- | --- | --- |
| **PM-001** | Створити новий проєкт з автоматичним планом | Створення запису проєкту | Проєкт створено, автоматично згенеровано `PLAN-001` (Generic Project Plan) |
| **PM-002** | Вибрати сховище артефактів (RepositoryProvider) | Вибір: Internal DB, Plain Git, GitHub, GitLab, Azure | Створено прив'язку `RepositoryBinding` без клонування репозиторію |
| **PM-003** | Заповнити базові розділи проєктного плану | Опис мети, обсягу робіт, команди (RACI) | Створено нову draft-ревізію плану з описовою структурою |
| **PM-004** | Відкрити сторінку модулів у проєктному плані | Перехід до секції `Модулі та розширення` | Відображено каталог глобально дозволених адміністратором модулів |
| **PM-005** | Активувати методологію Scrum або Waterfall | Вибір модуля `methodology.scrum` чи `waterfall` | У плані з'являються параметри каденції або послідовні фази |
| **PM-006** | Активувати галузевий комплаєнс ASPICE 4.0 | Вибір модуля `compliance.aspice` | У плані активовано VDA Scope (SYS.1..5, SWE.1..6) та правила трасованості |
| **PM-007** | Активувати модуль Functional Safety ISO 26262 | Вибір модуля `compliance.iso26262` | У плані активовано Safety Plan, додано поле `asil` до вимог, HARA-шаблони |
| **PM-008** | Сформувати графік фаз проєкту | Визначення дат початку/завершення фаз | Побудовано календарний план із контролем відсутності зациклень |
| **PM-009** | Створити майлстоун з каталогу типів віх | Вибір типу віхи з каталогу (Phase Gate, CDR) | Віху створено, автоматично додано обов'язкові критерії приймання |
| **PM-010** | Призначити обов'язкові артефакти до віхи | Прив'язка Deliverables до майлстоуну | Віха пов'язана з конкретними документами, що вимагають затвердження |
| **PM-011** | Затвердити базовий кошторис (Cost Baseline) | Фіксація планового бюджету за фазами/WBS | Створено версійований кошторис, визначено ліміти фінансування |
| **PM-012** | Налаштувати алокацію інженерних ресурсів | Розподіл фахівців за ролями та відсотками FTE | Сформовано план місткості, перевірено відсутність перевантаження |
| **PM-013** | Подати план проєкту на затвердження | Виклик команди `wp.submit` для плану | План переходить у стан `in_review`, формується ReviewRequest |
| **PM-014** | Застосувати незалежно погоджений план проєкту | Виклик `plan.apply` за окремим дозволом і чинним Approval | Зміни набувають чинності, оновлюються проєкції фаз і словників; PM не погоджує власну ревізію |
| **PM-015** | Переглянути дорожню карту проєкту (Roadmap) | Візуалізація графіка віх та фаз | Відображено діаграму з реальними статусами виконання |
| **PM-016** | Провести Gate Review для майлстоуну | Оцінка виконання критеріїв приймання віхи | Автоматична перевірка правил; при успіху створюється підписаний `GateDecision` |
| **PM-017** | Контролювати виконання бюджету (EVM аналіз) | Перегляд метрик $PV, AC, EV, CPI, SPI, EAC$ | Виявлення вартісних ($CV$) та календарних ($SV$) відхилень проєкту |
| **PM-018** | Обробити блокування від рушія правил (Veto) | Спроба порушення інваріанту (наприклад, без лінків) | Система блокує дію (HTTP 422) та видає сповіщення із поясненням |
| **PM-019** | Запросити виняток з правила (Waiver) | Подання обґрунтування та оцінки ризику уповноваженому погоджувачу | Рішення про `Waiver` з обмеженим строком ухвалює інша роль із явним правом; PM не обходить veto самостійно |
| **PM-020** | Зафіксувати релізний бейзлайн проєкту | Виклик операції `baseline.publish` | Перевірка закриття всіх обов'язкових віх, фіксація незмінного знімку артефактів |

## 3. Детальний опис ключових сценаріїв

### 3.1. Створення проєкту та вибір сховища (PM-001, PM-002)
1. Проєктний менеджер переходить у розділ `Projects` і натискає `New project`.
2. Вказує бізнес-код (`INV-CTRL-2026`) та назву проєкту.
3. Обирає тип підключення сховища:
   - *«Внутрішнє сховище DELMOS»* (миттєве створення без зовнішніх серверів);
   - або обирає провайдера (`GitHub`, `GitLab`, `Azure Repos`, `Plain Git`) і вказує репозиторій.
4. Система в одній транзакції:
   - Реєструє проєкт;
   - Створює обов'язковий `PLAN-001` (Generic Project Plan);
   - Заповнює початкові розділи та фіксує `ProjectPlanBinding`.

### 3.2. Керування фінансами та ресурсами (PM-011, PM-017)
1. У розділі `Бюджет та економіка` плану PM фіксує цільовий кошторис за статтями:
   - Оплата праці інженерів (Labor): 280 000 EUR;
   - Зразки мікроконтролерів та плат PCB: 45 000 EUR;
   - Ліцензії на компілятори та ПЗ: 25 000 EUR;
   - Резерв непередбачуваних витрат (Contingency): 35 000 EUR.
2. Протягом розробки інженери реєструють час через `WorkRecord`, а бухгалтерія вносить рахунки через `ExpenseRecord`.
3. Система в реальному часі розраховує Earned Value Management показники:
   - Planned Value ($PV$), Actual Cost ($AC$), Earned Value ($EV$);
   - Індекси ефективності: $CPI = EV / AC$, $SPI = EV / PV$;
   - Прогноз вартості завершення ($EAC$).
4. Якщо $CPI < 0.85$, система виставляє попередження у дашборді проєкту.

### 3.3. Проведення фазового шлюзу (Gate Review, PM-016)
1. При настанні дати віхи `Preliminary Design Review (PDR)` PM ініціює процедуру приймання.
2. Диспетчер правил перевіряє:
   - Чи всі обов'язкові результати (системні вимоги, HARA, архітектура) мають статус `approved`;
   - Чи відсутні відкриті критичні дефекти та незатверджені зміни;
   - Чи не перевищено встановлений ліміт фінансування етапу.
3. При повному дотриманні інваріантів підписується електронний запис `GateDecision: passed`, і проєкт отримує дозвіл на відкриття наступної інженерної фази.
