# DELMOS: журналювання та спостережуваність (Logging & Observability)

Дата: 2026-09-23. Статус: нормативний операційний посібник.
Ліцензія: Apache 2.0.
Контекст: [операційний посібник](RUNBOOK.md), [метрики та реєстр вимірювань](../architecture/METRICS.md).

---

## 1. Рівні журналювання

| Рівень | Призначення | Приклад події |
| --- | --- | --- |
| `DEBUG` | Детальна діагностика для розробки (вимкнено за замовчуванням у продуктивному середовищі) | Вміст SQL-запиту перед виконанням |
| `INFO` | Штатні операційні події | Успішний старт служби, застосована міграція, вхід користувача |
| `WARN` | Аномалії, що не зупиняють роботу | Аудиторське зауваження правила (`ADVISORY_WARNING`), сповільнена відповідь СУБД |
| `ERROR` | Помилки, що впливають на конкретний запит | Відхилена транзакція, порушення обов'язкового правила (`MANDATORY_VETO`) |
| `FATAL` | Критичні помилки, що зупиняють процес | Неможливість підключитися до бази даних під час старту |

## 2. Місце розташування журналів

* **Стандартний вивід (stdout/stderr):** перехоплюється `systemd` та доступний через `journalctl -u delmos`.
* **Файловий журнал (опціонально):** якщо увімкнено у конфігурації, записується в `/var/log/delmos/delmos.log` з ротацією через `logrotate`.

## 3. Політика ротації логів (`/etc/logrotate.d/delmos`)

```text
/var/log/delmos/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 delmos delmos
    sharedscripts
    postrotate
        systemctl kill -s USR1 delmos.service >/dev/null 2>&1 || true
    endscript
}
```

## 4. Що обов'язково журналюється

* Автентифікація (успішна та невдала), зміна прав доступу, відкликання сесій.
* Створення, погодження та застосування ревізій `Work Product` і `Generic Project Plan`.
* Спрацювання правил (`Rule`) із зазначенням вердикту (`passed`, `violated`, `not_applicable`, `evaluation_error`).
* Помилки доставки подій у черзі outbox (`event_deliveries`) та переведення в стан `dead_letter`.

## 5. Що НІКОЛИ не журналюється

* Паролі, токени доступу, секрети інтеграцій (`secret_ref`) або їх фрагменти.
* Повний вміст конфіденційних інженерних артефактів із грифом `restricted`.
* Персональні дані користувачів поза мінімально необхідним ідентифікатором (`user_id`) для цілей аудиту.

## 6. Розподілене трасування (Distributed Tracing)

Для інсталяцій Enterprise-рівня рекомендується інтеграція з відкритим стандартом **OpenTelemetry**:

1. Кожен вхідний HTTP-запит отримує унікальний `trace_id`, що поширюється через увесь ланцюжок обробки (HTTP-обробник → прикладний сервіс → SQL-транзакція → подія в черзі outbox).
2. Експорт трасувань здійснюється у форматі **OTLP** (OpenTelemetry Protocol) до стороннього колектора (наприклад, Jaeger, Grafana Tempo).
3. `trace_id` та `correlation_id` конверта події (див. [SPEC-04](../specifications/SPEC-04-EVENTS-TRIGGERS-RULES-ENGINE.md)) є одним і тим самим ідентифікатором, що дозволяє наскрізно простежити операцію від HTTP-запиту до фонової обробки в черзі.

## 7. Метрики експлуатації (Operational Metrics)

Технічні експлуатаційні показники (завантаження CPU, використання пам'яті, довжина черги outbox, затримка HTTP-відповіді) відокремлені від інженерних бізнес-метрик платформи (див. [METRICS.md](../architecture/METRICS.md)) і не зберігаються як домейнові події чи ревізії артефактів.
