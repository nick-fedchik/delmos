# DELMOS: оновлення версії та відкат (Upgrade & Rollback)

Дата: 2026-09-23. Статус: нормативний операційний посібник.
Ліцензія: Apache 2.0.
Контекст: [резервне копіювання та відновлення](BACKUP_AND_RESTORE.md), [вимоги до СУБД](../requirements/SYSTEM_REQUIREMENTS.md#3-вимоги-до-субд-postgresql-database-requirements).

---

Це цільовий runbook для майбутніх інсталяцій. Бінарника, служби та міграцій DELMOS наразі немає; наведені команди не призначені для виконання до реалізації й тестування цих можливостей.

## 1. Передумови

* Актуальна резервна копія бази даних створена безпосередньо перед початком оновлення (див. [BACKUP_AND_RESTORE.md](BACKUP_AND_RESTORE.md)).
* Нова версія бінарного файлу зібрана та перевірена командою `make validate`.
* Заплановане вікно обслуговування (maintenance window) погоджене з користувачами платформи.

## 2. Попередній перегляд міграцій

Перед зупинкою поточної служби рекомендується перевірити перелік міграцій, що будуть застосовані новою версією:

```bash
/usr/local/bin/delmos --migrate-plan
```

Команда виводить перелік ще не застосованих SQL-міграцій без внесення жодних змін до бази даних.

## 3. Застосування оновлення

1. Зупинити поточну службу: `sudo systemctl stop delmos`.
2. Створити резервну копію бази даних (обов'язковий крок, не пропускається навіть при незначному оновленні).
3. Замінити виконуваний файл: `sudo install -m 0755 delmos-new /usr/local/bin/delmos`.
4. Запустити службу: `sudo systemctl start delmos`.
5. Під час старту служба атомарно застосовує нові міграції під захистом консультативного блокування PostgreSQL (Advisory Lock), перевіряючи контрольні суми SHA-256 усіх попередньо застосованих файлів.
6. Перевірити готовність: `curl http://127.0.0.1:10120/readyz`.

## 4. Відкат при збої (Rollback on Failure)

Якщо після оновлення виявлено критичну несправність:

1. Зупинити службу нової версії: `sudo systemctl stop delmos`.
2. Відновити попередній бінарний файл: `sudo install -m 0755 delmos-previous /usr/local/bin/delmos`.
3. **Відновити базу даних із резервної копії, створеної перед оновленням** (пряме зменшення номера схеми без відновлення копії не підтримується — міграції є **forward-only**).
4. Запустити службу попередньої версії.

**Важливе правило:** forward-only модель міграцій означає, що стару версію бінарника не можна безпечно повернути назад на вже оновлену схему бази даних без явного відновлення резервної копії, зробленої до початку оновлення.

## 5. Оновлення через кілька версій (Multi-step Upgrade)

Якщо різниця між поточною та цільовою версією становить кілька релізів, оновлення виконується послідовно, версія за версією, без пропуску проміжних релізів, якщо офіційна документація релізу прямо не вказує на підтримку прямого стрибка.

## 6. Перевірка після оновлення

| Перевірка | Команда / Дія |
| --- | --- |
| Служба активна | `systemctl status delmos` |
| Готовність ядра та БД | `curl http://127.0.0.1:10120/readyz` |
| Версія бінарника | `/usr/local/bin/delmos --version` |
| Кількість застосованих міграцій | `psql -c "SELECT COUNT(*) FROM schema_migrations;"` |
| Доступність вебінтерфейсу | Відкрити застосунок у браузері та увійти під тестовим обліковим записом |

## 7. Типові несправності при оновленні

| Симптом | Ймовірна причина | Виправлення |
| --- | --- | --- |
| Служба не стартує після оновлення | Конфлікт контрольної суми міграції або пошкоджена схема | Відновити резервну копію, створену перед оновленням; повідомити команду архітектури |
| `/readyz` повертає 503 після старту | Тривале виконання великої міграції ще не завершено | Зачекати завершення міграції; перевірити журнал `journalctl -u delmos` |
| Втрата з'єднання клієнтів після оновлення | Реверс-проксі кешував застаріле з'єднання | Перезапустити реверс-проксі (Nginx/HAProxy) |
