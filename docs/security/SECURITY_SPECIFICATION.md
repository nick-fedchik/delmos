## 1. Шифрування даних у стані спокою (Encryption at Rest)

### 1.1. Категорії чутливих даних

| Категорія | Приклад | Вимога |
| --- | --- | --- |
| Секрети інтеграцій | Токен доступу до `RepositoryProvider`, ключ API зовнішньої системи | Шифрування на рівні застосунку перед записом у БД |
| Персональні дані | Адреса електронної пошти, повне ім'я користувача | Захист на рівні транспорту та обмеженого доступу (RBAC), без додаткового шифрування колонки за замовчуванням |
| Артефакти з грифом `restricted` | Інженерні документи з обмеженим доступом | Контроль доступу через ABAC (`classification`); шифрування сховища диска — відповідальність адміністратора ОС |

### 1.2. Алгоритм шифрування секретів

* **Алгоритм:** AES-256-GCM (автентифіковане шифрування, стійке до модифікації шифротексту).
* **Деривація ключа:** PBKDF2-HMAC-SHA256 з не менш ніж 100 000 ітерацій на основі майстер-ключа, що постачається через змінну середовища при старті процесу (див. [SYSTEM_REQUIREMENTS.md](../requirements/SYSTEM_REQUIREMENTS.md)), а не зберігається в конфігураційному файлі.
* **Зберігання:** застосунок ніколи не зберігає секрет у відкритому вигляді — лише посилання `secret_ref` (непрозорий ідентифікатор) та зашифрований блок у виділеній таблиці `encrypted_secrets`.

```sql
CREATE TABLE encrypted_secrets (
    secret_ref      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ciphertext      BYTEA NOT NULL,
    nonce           BYTEA NOT NULL,
    key_version     INTEGER NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    rotated_at      TIMESTAMPTZ
);
```

### 1.3. Ротація ключів

Майстер-ключ шифрування версіонується (`key_version`). Ротація виконується без простою: нові секрети шифруються поточною версією ключа, а існуючі перешифровуються фоновим завданням при плановому обслуговуванні.

## 2. Шифрування даних під час передачі (Encryption in Transit)

| З'єднання | Вимога |
| --- | --- |
| Браузер ↔ Реверс-проксі | TLS 1.3 (мінімально допустимо TLS 1.2 для сумісності зі старими клієнтами); заголовок `Strict-Transport-Security` обов'язковий |
| Реверс-проксі ↔ Процес DELMOS | Локальний loopback-інтерфейс без TLS (недоступний ззовні хоста) |
| Процес DELMOS ↔ PostgreSQL | Unix-сокет (без мережевого шифрування, оскільки з'єднання локальне та захищене правами файлової системи) |
| Процес DELMOS ↔ Зовнішній `RepositoryProvider` | Виключно HTTPS (порт 443); з'єднання без дійсного TLS-сертифіката відхиляється |

## 3. Керування секретами (Secrets Management)

| Секрет | Джерело | Правило |
| --- | --- | --- |
| Майстер-ключ шифрування | Змінна середовища процесу (`DELMOS_MASTER_KEY`) або файл з обмеженими правами `0600` | Ніколи не потрапляє в журнали, конфігураційні файли під контролем версій чи резервні копії у відкритому вигляді |
| Токени доступу `RepositoryProvider` | Вводяться адміністратором через захищену форму (write-only) | Після збереження ніколи не повертаються назад у відповіді API — лише `secret_ref` |
| Паролі бази даних | Автентифікація через Unix-сокет (peer/ident), паролі не використовуються для локальних з'єднань | Мережеві з'єднання (за потреби) вимагають `scram-sha-256` |

## 4. Безпека вебхуків (Webhook Security)

### 4.1. Верифікація підпису (HMAC-SHA256)

Кожен вхідний вебхук від зовнішнього `RepositoryProvider` супроводжується підписом у заголовку запиту. DELMOS обчислює HMAC-SHA256 від сирого тіла запиту з використанням спільного секрету, узгодженого під час налаштування інтеграції, та порівнює його з отриманим значенням у сталий за часом спосіб (`constant-time comparison`), щоб уникнути атак по часовому каналу (timing attack).

### 4.2. Захист від повторного відтворення (Replay Attack Prevention)

* Кожен вебхук містить часову мітку; запити старші за 5 хвилин відхиляються.
* Ідентифікатор доставки (`delivery_id`) фіксується у таблиці оброблених подій; повторна доставка з тим самим ідентифікатором ігнорується (ідемпотентність).
