# SWR-01: Системні вимоги до ядра проєктного плану та модульного вибору

Дата: 2026-09-23. Статус: нормативні вимоги підсистеми Core & Plan Engine.  
Ліцензія: Apache 2.0.  
Батьківські вимоги: [SHR-01](../stakeholder/SHR-01-generic-project-plan.md), [SHR-02](../stakeholder/SHR-02-module-system-policy.md), [SHR-03](../stakeholder/SHR-03-project-module-activation.md).  
Пов'язані архітектурні рішення: [ADR-004](../../architecture/decisions/ADR-004-two-tier-module-governance-generic-plan.md).

#### SWR-01: Автоматична генерація первинного плану при створенні проєкту
При виклику команди створення проєкту сервіс у межах однієї транзакції зобов'язаний:
1. Створити запис у таблиці `projects` зі статусом `initializing`.
2. Згенерувати обов'язковий Work Product `PLAN-001` (`type: plan`, `profile: core:project_plan`).
3. Створити першу immutable ревізію плану з базовою описовою структурою за замовчуванням.
4. Зареєструвати запис у `project_plan_bindings` із посиланням на створений WP.
5. Перевести проєкт у статус `active`.
6. Гарантувати рівно один `core:project_plan` у межах проєкту: `type: plan` і
	код `PLAN-001` зарезервовані для цього системного артефакту та не можуть бути
	створені через загальну команду створення Work Product. Майбутні спеціалізовані
	плани постачаються модулями як окремі профілі, а не як другий Project Plan.

#### SWR-02: Структурована конфігурація Generic Project Plan
1. Кожна ревізія `PLAN-001` повинна містити окремий типізований
	`GenericPlanManifest`; Markdown-тіло ревізії не є джерелом системних правил.
2. Маніфест базового Generic Plan повинен містити: `objectives`, `scope_items`,
	`assumptions`, `constraints`, `responsibility_assignments`, `deliverables`,
	`phases`, `milestones`, `acceptance_rules`, `governance` та `extensions`.
	Детальна модель визначена в
	[CORE-CONTRACT-003](../../specifications/CORE-CONTRACT-003-GENERIC-PLAN-DOMAIN-AND-AUTOMATION.md).
3. Кожна фаза має стабільний ідентифікатор, планові дати та залежності; граф
	залежностей фаз не може містити циклів.
4. Кожна віха належить одній фазі, має дату, пов'язані deliverables та базові
	критерії приймання. Deliverable посилається на Work Product того самого
	проєкту та визначає потрібний стан цього артефакту.
5. Ролі плану фіксують відповідальність і не надають RBAC-дозволів. Дозволи
	надаються тільки через `RoleBinding`.
6. Generic Plan не містить вбудованої семантики Scrum, Lean, V-Fall, галузевого
	комплаєнсу, бюджетів чи ресурсів. Такі правила та поля постачаються лише
	активними функціональними модулями.
7. Модульна конфігурація зберігається тільки у просторі
	`extensions.<module_id>` та проходить схему й валідацію цього модуля.
8. Базова версія Generic Plan є `revision_number`: натуральне число, що
	починається з `1` і монотонно збільшується для кожної незмінної ревізії
	`PLAN-001`. `manifest_version`, `profile_version` і `plan_schema_version`
	ідентифікують сумісність формату, а не версію плану. Модульні чи додаткові
	базові поля можуть вводити інші виміри версіонування, але не змінюють цієї
	послідовності. `row_version` є лише технічним токеном оптимістичного
	блокування конкурентних записів і не є версією плану.

#### SWR-03: Версіонування та життєвий цикл Project Plan
1. Зміна параметрів проєкту (ввімкнення модулів, зміна фаз, зміна правил) здійснюється виключно через створення нової draft-ревізії Project Plan.
2. Затвердження плану використовує спільний workflow WP, але вимагає окремого дозволу `plan.approve`, позитивної рецензії та незалежності автора; Approval фіксує точний `revision_id` і `payload_hash` ([ADR-009](../../architecture/decisions/ADR-009-core-review-and-approval-policy.md)).
3. Застосування плану (`plan.apply`) атомарно оновлює проекції проєкту в БД (`effective_plan_revision_id`, `config_generation`).

#### SWR-04: Реєстр системних модулів (Module Definition Registry)
1. Кожен модуль описується маніфестом: `id` із префіксом (`methodology.*`, `compliance.*`, `management.*`, `tooling.*`), `name`, `description`, `version` (SemVer), `category_id`, версії схем, `artifact_digest` та декларацією `extension_targets`.
2. Системний адміністратор змінює `ModuleSystemPolicy` (`available`, `blocked_for_new_activation`, `suspended`).
3. `blocked_for_new_activation` забороняє нові активації без зупинки чинних; `suspended` блокує виконання модуля в чинних проєктах.
4. Кожен `extension_target` явно визначає, яку сутність розширює модуль:
	`core:project_plan` або конкретний базовий/модульний профіль Work Product.
	Для кожної цілі маніфест містить тип внеску (`plan_section`,
	`property_extension`, `workflow_rule`, `milestone_type`, `ui_contribution`),
	версію JSON Schema та простір імен даних.
5. Ядро відхиляє конфігурацію або властивість, якщо вона не має активного модуля
	з відповідною декларацією `extension_target`.

#### SWR-05: Сторінка керування модулями в проєкті (Project Plan Modules Page)
1. В інтерфейсі редагування проєктного плану виділена секція `Модулі та розширення`.
2. Для нового вибору доступні лише globally available модулі. Вже використані blocked/suspended модулі залишаються видимими read-only з причиною.
3. При виборі модуля інтерфейс динамічно відображає його конфігураційну форму, валідовану за наданою модулем JSON Schema.
4. Нова ревізія стає effective лише після авторизованого погодження та виконання `plan.apply`.

#### Доповнення до SWR-03: виконання `plan.apply`
1. Фаза не переходить у статус `active`, доки хоча б одна фаза з її `depends_on` не має статусу `completed` (CORE-CONTRACT-002 §4.1).
2. Повторне застосування вже чинної ревізії плану ідемпотентне: не створює нового покоління конфігурації й не дублює запис у `project_plan_applications` (SWR-46.2).
3. Фаза чи віха, вилучена з маніфесту нової ревізії, вилучається і з проєкції після `plan.apply`. Якщо фаза вже має записану активність (`WorkRecord`, `ExpenseRecord`), вилучення відхиляється явним конфліктом — застаріла проєкція не залишається назавжди, але й не зникає мовчки разом зі своєю історією.
4. `plan.apply` записує коміт-подію `plan.applied` у той самій транзакції, що й проєкцію — це точка інтеграції для майбутніх споживачів (наприклад, реєстру метрик).
