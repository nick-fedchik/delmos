# SWR-10: Системні вимоги до доступу і незалежного погодження ядра

Дата: 2026-09-23. Статус: нормативні вимоги першого зрізу ядра.
Ліцензія: Apache 2.0.
Батьківська вимога: [SHR-14](../stakeholder/SHR-14-core-access-and-assurance.md).
Контекст: [ACCESS_CONTROL.md](../../architecture/ACCESS_CONTROL.md), [Work Products](../../architecture/WORK_PRODUCTS.md), [ADR-009](../../architecture/decisions/ADR-009-core-review-and-approval-policy.md), [UAT-004](../../uat/UAT-004-core-roles-review-approval.md).

#### SWR-42: Автентифікація та простір дії
1. Кожен інтерактивний запит із користувацькими даними потребує чинної серверної сесії; роль без активного `RoleBinding` не дає жодного дозволу.
2. Перевірка `actor + permission_key + resource + scope + classification + state` виконується сервером і при прямому URL/API-запиті, а не лише показом кнопки. Явне заперечення має перевагу над сумою дозволів.
3. Права Project не переходять до сусіднього Project; доступ до двох кінців міжпроєктного зв'язку перевіряється окремо. Список scope не розкриває назви недоступних об'єктів.

#### SWR-43: Базові ролі та матриця дозволів
1. `RoleDefinition` визначає ключі дозволів; `RoleBinding` містить scope, дату завершення та підставу делегування. Жодна базова роль не призначається всім користувачам автоматично.
2. Мінімальні дозволи першого зрізу: Viewer — `project.read`, `wp.read` у призначеному scope; Engineer — `wp.create`, `wp.edit`, `wp.submit`; Reviewer — `wp.review`, `wp.request_changes`; Approver — `wp.approve`, `wp.request_changes`; Auditor — `wp.history.read`, `audit.read` для дозволених записів; Project Manager — створення проєкту за явним дозволом `scopes.manage`, `plan.edit`, `wp.submit`, `plan.apply`; System Administrator — `identities.manage`, `access.grant`, `access.revoke`, системні політики без неявного `wp.approve`. Читання об'єкта, потрібного для дії, надається явною прив'язкою в її scope, а не мовчазним суперправом.
3. Поєднання ролей не скасовує SoD; доступ до `baseline.read`, `wp.history.read` для Viewer, `baseline.publish`, експорту, налаштувань модулів, ставок і галузевих погоджень визначається окремими дозволами. Одна назва ролі не дає всіх майбутніх можливостей PM/ADM.
4. Адміністратор не може самопризначенням або делегуванням вище власної стелі отримати незалежний інженерний підпис; кожне надання/відкликання прив'язки аудитується.

#### SWR-44: Видимість при читанні, пошуку та експорті
1. `project.read`, `wp.read`, `wp.history.read`, `baseline.read` та окреме право експорту перевіряються незалежно; читання не означає право масового експорту.
2. Перевірки застосовуються до списків, кількостей, пошуку, графа, вектора, вкладеного елемента композитної специфікації та експорту; невидимий об'єкт не розкриває навіть назву в повідомленні про помилку.
3. При недоступному елементі повний експорт композитної специфікації блокується або створюється тільки за окремо визначеною політикою redaction; поточне UI-фільтрування не замінює серверний контроль.

#### SWR-45: Незалежні рецензія та затвердження WP
1. `wp.submit` фіксує точну ревізію й переводить її в `in_review`; `wp.review` записує висновок Reviewer, але не затверджує WP; `wp.approve` є окремим рішенням Approver.
2. Для базового workflow потрібен щонайменше один позитивний Review і один Approval на **той самий** `revision_id`/`payload_hash`; Reviewer і Approver можуть бути тією самою особою тільки за обома явними RoleBindings, але жоден з них не може бути автором ревізії. Посилені правила модулів можуть збільшити кворум, але не послабити цю межу.
3. `wp.request_changes` повертає ревізію в `draft` з мотивованим записом, а не вводить неописаний статус `rejected`; після нової ревізії попередні Review/Approval не переносяться автоматично.
4. За зміни ревізії, втрати права, простроченого рішення чи повторного запиту сервер повертає конфлікт або той самий ідемпотентний результат без дублювання підпису. Автор не може обійти SoD через прямий API чи суму ролей.

#### SWR-46: Незалежне застосування плану і винятків
1. `plan.approve` підпорядковується тим самим правилам незалежності автора та точного хешу; лише **після** Approval окрема команда `plan.apply` користувача з її явним дозволом робить цю ревізію чинною.
2. Наявність `plan.apply` без Approval або на іншій ревізії не змінює `effective_plan_revision_id`; повтор застосування тієї самої ревізії ідемпотентний.
3. Блокуючий veto не може бути обійдений діалогом підтвердження; waiver потребує окремого запису, дозволу й незалежного рішення уповноваженої ролі, яке не входить до базового `wp.approve`.

#### SWR-47: Докази рішень та аудиторський доступ
1. Кожен Review, Approval, відкликання права й застосування плану фіксує актора, роль/scope, час, correlation ID, `revision_id` і хеш там, де він є, без секретів у журналі.
2. Auditor із `audit.read` та дозволеним доступом до відповідних ревізій читає ці записи, але не може змінювати, погоджувати, призначати роль чи експортувати закриті дані без окремих прав.
3. Погоджений WP, його точні ревізії й рішення не видаляються через звичайне архівування проєкту; строк утримання та допустиме очищення технічних даних визначаються окремою політикою доказів.

#### SWR-48: Відкликання й повторна перевірка доступу
1. Відкликання/сплив RoleBinding змінює результат наступного API-запиту й прямого deeplink навіть при чинній браузерній сесії; прихована кнопка не вважається механізмом відкликання.
2. Фонові задачі перед використанням об'єкта повторно перевіряють чинні дозволи й classification; за відмови доставка не розкриває payload неуповноваженому зовнішньому одержувачу.
3. Тести охоплюють активну сесію після відкликання, два проєкти, прямий API, Reviewer без `wp.approve`, самопогодження автора, Auditor без write/export та конфлікт ревізій; результати пов'язуються з [UAT-004](../../uat/UAT-004-core-roles-review-approval.md).
