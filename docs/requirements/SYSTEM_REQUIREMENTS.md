## 1. Вступ та навігація до функціональних вимог

Платформа **DELMOS** (Discovery, Engineering & Lifecycle Management Operating System) розгортається як високопродуктивний модульний моноліт у вигляді єдиного Go-бінарника із вбудованим SPA-фронтендом під нативним керуванням операційної системи Linux (Ubuntu 26.04/24.04 LTS) та СУБД PostgreSQL.

### Розподіл вимог платформи:
* **Функціональні інженерні та стейкхолдерські вимоги** винесено в окремі ієрархічні нормативні документи:
  * **[Ієрархічні вимоги до системи (Методологія та каталог)](README.md)**
   * **[Стейкхолдерські вимоги (SHR-01..14)](stakeholder/README.md)** — вимоги стейкхолдерів до процесів, плану, моделей та безпеки.
   * **[Системні вимоги до підсистем (SWR-01..48)](software/README.md)** — декомпозиція вимог за 10 підсистемами ядра, специфікацій, автоматизації та економіки.
* **Цей документ (`SYSTEM_REQUIREMENTS.md`)** є нормативним стандартом технічного середовища: він регламентує вимоги до інструментів збірки, робочого середовища розробника, параметрів СУБД PostgreSQL, конфігурації ОС Linux, ієрархії каталогів FHS, прав доступу, служби `systemd` та мережевих інтерфейсів.

## 2. Вимоги до середовища розробки (Development Environment)

### 2.1. Інструментарій бекенду (Go Toolchain)
1. **Версія компілятора:** Go версії 1.22+ (цільова версія 1.26), архітектури `linux/amd64` або `linux/arm64`.
2. **Модульна система:** стандартний `go.mod` із назвою модуля `delmos`.
3. **CGO-Free:** збірка здійснюється без використання CGO (`CGO_ENABLED=0`), що гарантує максимальну переносимість і стабільність бінарного файлу.
4. **Мережевий шар:** використання стандартної бібліотеки `net/http` з нативною маршрутизацією методів (Go 1.22+ routing enhancements).
5. **Робота з БД:** чистий SQL драйвер `github.com/jackc/pgx/v5` із пулом з'єднань `pgxpool`.
6. **Валідація метаданих:** валідатор JSON Schema Draft 2020-12 (`github.com/santhosh-tekuri/jsonschema/v6`).

### 2.2. Інструментарій фронтенду (Frontend Toolchain)
1. **Середовище виконання:** Node.js версії 20.x LTS або 22.x LTS (перевірено на v22.22.1).
2. **Менеджер пакетів:** `npm` версії 9+ (використання прапорця `--legacy-peer-deps` при інсталяції через специфіку версіонування залежностей дизайн-системи).
3. **Фреймворк:** Vue 3 (версія 3.5+), Composition API, `<script setup lang="ts">`.
4. **Типізація:** TypeScript версії 5.x, строгий режим (`strict: true`), перевірка типів через `vue-tsc`.
5. **Збирач:** Vite версії 6.x (`@vitejs/plugin-vue`).
6. **Дизайн-система:** дизайн-токени та стилістичні утиліти GitLab Pajamas (`@gitlab/ui`), шрифти `@gitlab/fonts`, іконки `@gitlab/svgs`.
7. **Векторна графіка:** компонентна база `Vue Flow` на базі SVG для інтерактивних графів та бібліотека `mermaid` для декларативного рендерингу діаграм у документації.
8. **Тестування:** `vitest` (версія 5.x+) із середовищем `jsdom` для компонентних та інтеграційних тестів інтерфейсу.

### 2.3. Операційні утиліти розробника
* **GNU Make:** єдиний інтерфейс виконання інженерних операцій через `Makefile`.
* **Git:** система контролю версій для відстеження змін у репозиторії.
* **Лінтери:** `gofmt`, `go vet`, `eslint` (flat config `eslint.config.js` з плагінами `typescript-eslint` та `eslint-plugin-vue`).

### 2.4. Ворота перевірки якості (Validation Gate)
Кожна зміна коду повинна проходити повну перевірку:
```bash
make validate
```
Реалізований обсяг (фаза P0): форматування Go (`gofmt`), статичний аналіз (`go vet`, `golangci-lint`), модульні тести (`go test -race`), перевірка відносних посилань Markdown-документації та збірка бінарника без CGO із `-trimpath`.

Цільовий обсяг після появи фронтенду та інсталяційних артефактів додатково охоплює:
1. Типізацію Vue/TypeScript (`vue-tsc`).
2. Лінтування фронтенду (`npm run lint`).
3. Тести інтерфейсу (`npm run test:unit`).
4. Синтаксичну коректність файлу `sudoers` (`visudo -cf`).
5. Складання фронтенду (`npm run build`) та синхронізацію вбудованих активів.

## 3. Вимоги до СУБД PostgreSQL (Database Requirements)

Платформа DELMOS повністю спирається на архітектуру **All-in-PostgreSQL** ([ADR-001](../architecture/decisions/ADR-001-all-in-postgresql-storage.md)).

### 3.1. Версія та необхідні розширення
1. **Версія СУБД:** PostgreSQL 16+; 18.6 є цільовим середовищем майбутніх інтеграційних і навантажувальних тестів, не протестованою версією DELMOS.
2. **Обов'язкові розширення:**
   * **`pgvector`** (версія 0.8.0+): тип даних `vector`, HNSW-індекси та оператори косинусної відстані (`<=>`) для семантичного пошуку дублікатів та рекомендації зв'язків.
   * **`ltree`**: тип даних для матеріалізованих ієрархічних шляхів, що забезпечує миттєвий GiST-індексний пошук у деревах специфікацій та WBS.

### 3.2. Підключення та безпека мережі СУБД
1. **Локальний транспорт:** з'єднання між сервісом DELMOS та PostgreSQL здійснюється виключно локально через високошвидкісний UNIX-сокет (`/var/run/postgresql`) або локальний loopback (`127.0.0.1:5432`).
2. Порт PostgreSQL ніколи не публікується назовні у відкриту мережу.

### 3.3. Розподіл ролей та прав доступу (Privilege Separation)
Для забезпечення максимальної безпеки інфраструктури база даних використовує принцип розділення привілеїв:
1. **Роль мігратора (`delmos_migrator`):**
   * Використовується виключно під час старту застосунку для накатування міграцій.
   * Є власником схеми даних, таблиць та об'єктів DDL.
2. **Робітнича роль застосунку (`delmos`):**
   * Використовується рантаймом для виконання щоденних операцій користувачів.
   * Має `USAGE` на схеми та лише необхідні для конкретних таблиць `SELECT`, `INSERT`, `UPDATE`, `DELETE`; для незмінного `audit_events` дозволені `INSERT` та авторизований `SELECT`, але **не** `UPDATE`, `DELETE` чи `TRUNCATE`. Не має права `CREATE SCHEMA`, `DROP TABLE` або `ALTER TABLE`.
   * Це повністю запобігає ризику руйнування схеми при можливих вразливостях прикладного шару (SQL Injection Mitigation).

### 3.4. Керування міграціями
1. Міграції вбудовуються безпосередньо у бінарний файл за допомогою директиви Go `//go:embed sql/*.sql`.
2. Застосування міграцій серіалізується за допомогою сесійних консультативних блокувань (**PostgreSQL Advisory Locks**, ключ `7108ecb72639`), що запобігає гонитві при паралельному старті кількох інстансів.
3. Кожна міграція має контрольний хеш SHA-256; зміна раніше накачаного SQL-файлу негайно блокує старт сервісу для запобігання пошкодженню даних.

### 3.5. Резервне копіювання та репетиція відновлення (Backup & Restore Rehearsal)
1. **Формат дампу:** кастомний стиснений формат `pg_dump -Fc`, що зберігає реляційні таблиці, зв'язки трасованості та вектори `pgvector`.
2. **Цілісність:** створення дампу супроводжується обов'язковою генерацією файлу контрольної суми `sha256sum`.
3. **Регулярна перевірка (`make restore-check`):** автоматизований скрипт розгортає створений дамп у тимчасову тестову базу даних під керуванням DBA, перевіряє кількість міграцій і сутностей та безпечно видаляє тестову базу після перевірки.

## 4. Вимоги до середовища виконання в Linux (Runtime Environment)

### 4.1. Операційна система та ядро
* **Дистрибутив:** Ubuntu Linux 24.04 LTS або 26.04 LTS (нативна інсталяція без Docker).
* **Архітектура процесора:** `x86_64` (amd64) або `aarch64` (arm64).
* **Система ініціалізації:** `systemd` версії 255+.

### 4.2. Апаратні ресурси сервера (Hardware Sizing)
| Рівень інсталяції | Кількість користувачів / артефактів | vCPU | Оперативна пам'ять (RAM) | Дисковий простір (NVMe SSD) |
| --- | --- | --- | --- | --- |
| **Мінімальний (PoC / R&D)** | До 20 користувачів, до 10 000 вимог | 2 vCPU | 4 GB RAM | 20 GB |
| **Стандартний (Проєктна команда)** | До 100 користувачів, до 100 000 вимог | 4 vCPU | 8–16 GB RAM | 50–100 GB |
| **Enterprise / Корпоративний** | 500+ користувачів, 500 000+ артефактів | 8–16 vCPU | 32–64 GB RAM | 250+ GB NVMe |

*Примітка щодо RAM:* Використання векторних індексів HNSW у `pgvector` вимагає утримання векторного графа в оперативній пам'яті. Для інсталяцій на 100 000+ ревізій із розмірністю вектора 1536 виділяється щонайменше 8 ГБ оперативної пам'яті виключно під параметри PostgreSQL `shared_buffers` та робочу пам'ять.

### 4.3. Системний користувач та група
* Сервіс виконується від імені спеціального виділеного системного користувача:
  ```bash
  sudo useradd --system --no-create-home --shell /usr/sbin/nologin --user-group delmos
  ```
* Заборонено запуск процесу DELMOS від імені `root`.

### 4.4. Стандартизована ієрархія каталогів FHS (Filesystem Hierarchy Standard)
Система встановлюється за суворими правилами стандарту FHS:

| Шлях у файловій системі | Призначення | Права доступу | Власник |
| --- | --- | --- | --- |
| `/usr/local/bin/delmos` | Виконуваний бінарний файл сервера | `0755` (`rwxr-xr-x`) | `root:root` |
| `/usr/local/etc/delmos/` | Директорія конфігурації платформи | `0750` (`rwxr-x---`) | `root:delmos` |
| `/usr/local/etc/delmos/delmos.yaml` | Головний конфігураційний файл (без відкритих паролів) | `0640` (`rw-r-----`) | `root:delmos` |
| `/usr/local/etc/delmos/delmos.env` | Файл захищених змінних середовища та паролів БД | `0600` (`rw-------`) | `root:root` |
| `/var/lib/delmos/` | Сховище даних, bare Git-репозиторії, вкладення | `0750` (`rwxr-x---`) | `delmos:delmos` |
| `/var/log/delmos/` | Файлові журнали операцій (якщо увімкнено) | `0750` (`rwxr-x---`) | `delmos:delmos` |
| `/etc/systemd/system/delmos.service`| Опис служби systemd | `0644` (`rw-r--r--`) | `root:root` |
| `/etc/sudoers.d/delmos` | Політика дозволених дій без пароля для оператора | `0440` (`r--r-----`) | `root:root` |

## 5. Вимоги до налаштування запуску в Linux (Service Configuration)

### 5.1. Конфігурація служби Systemd (`delmos.service`)
Служба реєструється як нативний демон операційної системи:

```ini
[Unit]
Description=DELMOS (Discovery, Engineering & Lifecycle Management Operating System)
Documentation=https://github.com/nick-fedchik/delmos
After=network.target postgresql.service
Wants=postgresql.service

[Service]
Type=simple
User=delmos
Group=delmos
ExecStart=/usr/local/bin/delmos
WorkingDirectory=/var/lib/delmos
EnvironmentFile=-/usr/local/etc/delmos/delmos.env
Restart=always
RestartSec=5s

# Безпека та ізоляція процесу Linux
LimitNOFILE=65536
ProtectSystem=full
ProtectHome=true
NoNewPrivileges=true
PrivateTmp=true

# Тайм-аут коректного завершення
TimeoutStopSec=15s

[Install]
WantedBy=multi-user.target
```

### 5.2. Коректне завершення роботи (Graceful Shutdown)
1. При отриманні сигналів `SIGINT` або `SIGTERM` сервер DELMOS негайно припиняє прийом нових вхідних HTTP-з'єднань.
2. Процес виділяє до 15 секунд на:
   * завершення активних SQL-транзакцій;
   * коректне скидання оренди повідомлень у черзі outbox (`release leases`);
   * закриття пулу з'єднань `pgxpool`.

### 5.3. Моніторинг працездатності (Liveness & Readiness Endpoints)
Сервер надає стандартизовані діагностичні ендпоінти:
* **`/healthz` (Liveness):** повертає HTTP 200, якщо процес живий та готовий приймати запити.
* **`/readyz` (Readiness):** повертає HTTP 200 лише за умови успішного пінгу СУБД PostgreSQL та перевірки цілісності схеми даних. Якщо база даних недоступна, повертається HTTP 503 Service Unavailable, запобігаючи маршрутизації клієнтського трафіку реверс-проксі.

### 5.4. Політика Sudoers (`/etc/sudoers.d/delmos`)
Для автоматизації операцій CI/CD та дій оператора хоста налаштовується файл із мінімальними правами без запиту пароля (`NOPASSWD`):
* Дозволені команди: запуск, зупинка, перезапуск та статус служби (`systemctl start/stop/restart/status delmos`), створення робочих директорій та встановлення бінарника в `/usr/local/bin/delmos`.
* Будь-які модифікації юніт-файлу чи доступ до паролів адміністратора вимагають повної авторизації DBA/Root.

## 6. Вимоги до мережі та інтеграційних контурів

### 6.1. Реверс-проксі та термінація TLS
* Застосунок DELMOS працює за реверс-проксі сервером (Nginx або HAProxy).
* **Порт застосунку:** за замовчуванням `127.0.0.1:10020`. Заборонено пряму публікацію порту 10020 у зовнішні незахищені мережі.
* **Термінація TLS:** реверс-проксі забезпечує протокол HTTPS (TLS 1.3/1.2) із валідними сертифікатами.
* **Заголовки безпеки:** обов'язкова передача заголовків `X-Forwarded-For`, `X-Forwarded-Proto: https`, `Strict-Transport-Security` (HSTS) та політики `SameSite=Strict` для сесійних cookies.

### 6.2. Мережева доступність провайдерів сховищ (`RepositoryProvider`)
Сервер DELMOS вимагає дозволу вихідного мережевого трафіку до підключених зовнішніх систем:
* **Порт 443 (HTTPS):** вихідні REST API запити до GitHub (`api.github.com`), GitLab (SaaS або корпоративний On-Premise інстанс), Azure DevOps (`dev.azure.com`), Bitbucket, Forgejo/Gitea, а також до провайдерів автентифікації OIDC / SAML / OAuth.
* **Порт 22 (SSH):** вихідні з'єднання при використанні чистого віддаленого Git (`plain_git`) за протоколом SSH.
* Якщо система розгортається в повністю ізольованому контурі (Air-Gapped Environment), використовується внутрішнє сховище (`internal`), що не вимагає жодних зовнішніх мережевих підключень.
