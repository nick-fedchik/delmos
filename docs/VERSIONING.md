# DELMOS: політика версіонування (Versioning)

Дата: 2026-09-23. Статус: нормативна політика версіонування релізів.
Ліцензія: Apache 2.0.
Контекст: [дорожня карта](architecture/ROADMAP.md), [шаблон нотаток релізу](templates/RELEASE-NOTES-TEMPLATE.md).

---

## 1. Єдина версія продукту

DELMOS постачається як єдиний бінарник, що обслуговує і backend API, і скомпільований frontend SPA. Тому продукт має **єдиний уніфікований номер версії** (`vMAJOR.MINOR.PATCH`), спільний для backend та frontend — не існує окремих версій «версія API» та «версія інтерфейсу», що розходяться між собою.

Джерело істини для поточної версії:

* Backend: `internal/version/version.go`
* Frontend (лише якщо виправлення стосується виключно UI без зміни backend): `web/package.json`

## 2. Правила семантичного версіонування

| Приріст | Коли застосовується | Приклад |
| --- | --- | --- |
| **MAJOR** | Незворотно несумісна зміна контракту API, схеми бази даних без автоматичної міграції, або видалення публічної можливості | `v1.4.2 → v2.0.0` |
| **MINOR** | Додано нову користувацьку можливість (наприклад, новий опційний модуль комплаєнсу) без порушення зворотної сумісності | `v1.4.2 → v1.5.0` |
| **PATCH** | Виправлення дефекту чи внутрішнє вдосконалення без зміни спостережуваної поведінки API | `v1.4.2 → v1.4.3` |

### 2.1. Релізи до `v1.0.0`

Доки не опубліковано `v1.0.0`, публічні контракти (REST API, схема БД, формат конфігурації) є **нестабільними**: несумісна зміна допускається в межах приросту MINOR (`v0.y.z → v0.(y+1).0`) із обов'язковим записом у нотатках релізу та міграцією схеми. З моменту `v1.0.0` діють повні гарантії з таблиці вище. Релізи `v0.y.z` позначаються як `alpha` і не придатні для виробничого використання.

## 3. Обсяг релізу `v1.0.0` (Minimal Viable Product)

`v1.0.0` — це **перший замкнений робочий цикл**: адміністратор входить у систему, створює проєкт із обов'язковим планом, веде базові артефакти та зв'язує проєкт із Git-сховищем.

### 3.1. Увійшло до обсягу

| # | Можливість | Межа реалізації у `v1.0.0` |
| --- | --- | --- |
| 1 | **Автентифікація адміністратора** | Локальний вхід (логін/пароль), серверні HttpOnly-сесії, CSRF-захист, rate-limiting, роль `administrator` та базовий Scoped RBAC. Без OIDC/SAML та самореєстрації користувачів. |
| 2 | **CRUD проєкту** | Створення, читання, редагування та архівація `Project` із членством (`ProjectMembership`). `Programme` — опційно, без ієрархічної агрегації показників. |
| 3 | **План проєкту** | Атомарне створення обов'язкового `Generic Project Plan` (`PLAN-001`) разом із проєктом (`ProjectPlanBinding`), редагування його вмісту. Без каталогу модулів, чернетки плану та `plan apply`. |
| 4 | **CRUD базового Work Product** | Створення та редагування артефактів 6 типів ядра (`plan`, `requirement`, `architecture`, `test_spec`, `report`, `record`) із незмінними ревізіями та `payload_hash`. Без композитних специфікацій і кворумного погодження. |
| 5 | **Просте Git-сховище** | Один провайдер: чистий Git (локальний bare або віддалений по SSH/HTTPS) за інтерфейсом `RepositoryProvider`: прив'язка до проєкту, перегляд гілок і комітів, експорт ревізій Docs-as-Code. Без адаптерів GitHub/GitLab/Azure DevOps/Bitbucket/Forgejo. |
| 6 | **Мінімальний Web GUI** | Екрани входу, списку/картки проєкту, плану та артефактів — рівно стільки, скільки потрібно для сценаріїв 1–5 без обходу серверного контракту. |
| 7 | **Експлуатаційний мінімум** | `make validate`, міграції з контрольними сумами, `systemd`-одиниця, перевірені backup/restore, структуроване логування та аудит дій адміністратора. |

### 3.2. Свідомо поза межами `v1.0.0`

Векторний пошук (`pgvector`), рекурсивний граф трасованості та RTM, композитні специфікації (SPEC-01..10), рушій подій/правил і планувальник, проєктна економіка та EVM, адаптери зовнішніх платформ, каталог галузевих модулів (ASPICE, ISO 26262, ISO 21434) та SVG-візуалізація графів плануються на `v1.x`–`v2.x` за [дорожньою картою](architecture/ROADMAP.md). Їхня відсутність у `v1.0.0` не є приводом заявляти про них як про наявні можливості.

### 3.3. Критерії випуску `v1.0.0`

* Наскрізний сценарій *вхід → створення проєкту з `PLAN-001` → створення й редагування WP → прив'язка Git-сховища* проходить автоматизовано та підтверджений UAT.
* Кожна можливість із таблиці 3.1 має відповідні SHR/SWR та запис у [матриці трасованості](TRACEABILITY.md).
* Негативні тести доступу (чужий проєкт, `restricted` поля, CSRF, підбір пароля) проходять у CI.
* REST-контракт зафіксований контрактними тестами проти [OpenAPI](api/openapi.core.v1.yaml) — саме він стає об'єктом гарантій сумісності SemVer.
* Документована інсталяція та перевірена процедура оновлення/відкоту.

## 4. Політика тегів

* Кожен реліз позначається анотованим (`annotated`) Git-тегом у форматі `vMAJOR.MINOR.PATCH`.
* Теги є **незмінними**: після публікації тег ніколи не переміщується на інший коміт.
* Перед мажорним чи мінорним релізом обов'язково виконується повний прогін чотирьох рівнів тестування (див. [testing/TEST_STRATEGY.md](testing/TEST_STRATEGY.md)).

## 5. Чек-ліст релізу

1. Усі задачі, заплановані на реліз, закриті або свідомо перенесені з поясненням.
2. `make validate` пройдено без помилок на гілці релізу.
3. `CHANGELOG.md` оновлено записом за шаблоном [RELEASE-NOTES-TEMPLATE.md](templates/RELEASE-NOTES-TEMPLATE.md).
4. Номер версії піднято одночасно в `internal/version/version.go` та (за потреби) `web/package.json`.
5. Створено анотований Git-тег `vX.Y.Z`.
6. Резервна копія бази даних створена безпосередньо перед розгортанням оновлення (див. [operations/UPGRADE_AND_ROLLBACK.md](operations/UPGRADE_AND_ROLLBACK.md)).
